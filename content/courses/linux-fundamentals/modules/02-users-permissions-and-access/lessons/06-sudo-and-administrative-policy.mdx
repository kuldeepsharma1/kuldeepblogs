## **1. Introduction**

Now we move from file access to administrative privilege.

Imagine a Linux server.

You have ten developers, three administrators and several service accounts.

Should every developer have full root access?

No.

But developers may need to perform certain administrative operations.

For example:

- Restart an application service.
- Inspect service status.
- Read selected system logs.
- Deploy an application.
- Install approved packages.
- Edit specific configuration files.

Giving all developers unrestricted root access would be dangerous.

Linux uses `sudo` to delegate administrative privileges in a controlled way.

The objective is:

> Allow users to perform specific privileged operations without giving them unrestricted administrative control.

## **2. Conceptual Foundation**

### **2.1 What is sudo?**

`sudo` means **Superuser Do**.

It lets an authorized user execute a command with another user's privileges, commonly root.

Example:

```
sudo apt update
```

The command normally runs with root privileges.

Another example:

```
sudo systemctl restart nginx
```

This executes the service-management command with elevated privileges, assuming the user is authorized and the environment supports the relevant service manager.

### **2.2 Why not always log in as root?**

Running an entire interactive session as root increases the risk of mistakes.

For example:

```
rm -r important-directory
```

A mistake made by an unrestricted root shell can have much greater consequences than one made by a normal user.

With `sudo`, privileged access can be limited to specific commands or administrative tasks.

Advantages include:

- More limited privilege.
- Better accountability.
- Centralized privilege policy.
- Administrative command logging.
- Less need to share the root password.
- Easier delegation and removal of privileges.

### **2.3 What happens when sudo is executed?**

A simplified flow:

```
User runs sudo command
        │
        ▼
sudo identifies the invoking user
        │
        ▼
sudo evaluates policy
        │
        ├── Is the command permitted?
        │
        ├── Is the target user permitted?
        │
        └── Is authentication required?
        │
        ▼
If authorized:
        │
        ▼
Command runs using requested privileges
        │
        ▼
Result returned to invoking user
```

`sudo` is not a mechanism that grants every user root access automatically.

It checks an authorization policy.

## **3. Windows-to-Linux Comparison**

| Windows                    | Linux                            |
| -------------------------- | -------------------------------- |
| Run as administrator       | `sudo command`                   |
| User Account Control (UAC) | Privilege elevation through sudo |
| Local security policy      | sudoers policy                   |
| Administrator group        | Often `sudo` or `wheel` group    |
| Run as different user      | `sudo -u user`                   |
| Administrative terminal    | Root shell through `sudo -i`     |

The concepts are comparable, but the mechanisms and policies differ.

In Windows, a user may receive a UAC prompt when an application requests elevation.

In Linux, `sudo` checks the sudoers policy and may ask for the invoking user's password.

## **4. Basic sudo Commands**

### **4.1 Execute a command with elevated privileges**

```
sudo apt update
```

This runs package metadata updates with the privileges required to access and update system package information.

### **4.2 Display allowed sudo commands**

```
sudo -l
```

This displays the commands your user is permitted to execute through sudo.

For a typical WSL Ubuntu user, you may see a rule similar to:

```
User developer may run the following commands:
    (ALL : ALL) ALL
```

The actual output depends on the system configuration.

### **4.3 Run a command as another user**

```
sudo -u labuser whoami
```

Expected:

```
labuser
```

The `-u` option specifies the target user.

Run as a group where permitted:

```
sudo -g developers command
```

The `-g` option selects the target group.

### **4.4 Run a login shell as root**

```
sudo -i
```

This starts an interactive root login-style shell.

Your prompt may change:

```
developer@linux:~$
```

to:

```
root@linux:~#
```

Exit when done:

```
exit
```

### **4.5 Run a shell with root privileges**

```
sudo -s
```

This starts a root shell, generally using the current environment rather than a full login environment.

The distinction:

| Command                 | Purpose                                  |
| ----------------------- | ---------------------------------------- |
| `sudo command`          | Run one command with elevated privileges |
| `sudo -u alice command` | Run command as Alice                     |
| `sudo -i`               | Start a root login shell                 |
| `sudo -s`               | Start a privileged shell                 |

Prefer one-command elevation when possible.

### **4.6 Validate or refresh authentication**

```
sudo -v
```

Validates or refreshes the user's sudo authentication credentials without executing a command.

### **4.7 Invalidate cached authentication**

```
sudo -k
```

Invalidates cached sudo credentials for the current user.

The next protected command may require authentication again.

## **5. Understanding sudo Policy**

The main policy file is:

```
/etc/sudoers
```

Additional policy files are commonly stored in:

```
/etc/sudoers.d/
```

Inspect the main file without modifying it:

```
sudo less /etc/sudoers
```

The exact file contents vary, but Ubuntu commonly includes a rule similar to:

```
%sudo ALL=(ALL:ALL) ALL
```

Let's understand this syntax.

### **5.1 Understanding a sudoers rule**

Example:

```
%sudo ALL=(ALL:ALL) ALL
```

Breakdown:

| Section     | Meaning                                           |
| ----------- | ------------------------------------------------- |
| `%sudo`     | Members of the `sudo` group                       |
| First `ALL` | Applies on all hosts matching this policy context |
| `(ALL:ALL)` | Can run as any target user and group              |
| Final `ALL` | Can execute any command                           |

This is broad administrative permission.

It is appropriate for a trusted administrator group in many installations, but not necessarily for ordinary developers or service accounts.

### **5.2 User-specific rule**

Example:

```
alice ALL=(root) /usr/bin/systemctl status nginx
```

Conceptually, this permits Alice to run the specified command as root on applicable hosts.

A command-specific rule should use the actual command path and be tested carefully.

However, a command's arguments, its own behavior, and what it allows the user to execute indirectly must also be considered.

For example, allowing an unrestricted editor or shell through sudo can effectively provide unrestricted root access.

### **5.3 Group-specific rules**

The `%` prefix indicates a group:

```
%developers ALL=(root) /usr/bin/systemctl status nginx
```

This grants members of `developers` the configured permission.

It does not mean every developer automatically receives root privileges. The actual command authorization depends on the full rule.

### **5.4 Run-as specification**

Consider:

```
alice ALL=(postgres) /usr/bin/psql
```

Alice is allowed to run the specified command as the `postgres` user, subject to the command rule and system configuration.

The target identity does not have to be root.

This is useful for controlled administration of a service account.

## **6. Sudoers Syntax: The Building Blocks**

A simplified rule format is:

```
WHO HOST = (RUNAS) COMMANDS
```

Example:

```
alice ALL=(root) /usr/bin/systemctl status nginx
```

There are also useful alias definitions.

### **6.1 User_Alias**

Groups users into a named policy alias.

```
User_Alias WEBADMINS = alice, bob
```

### **6.2 Runas_Alias**

Groups target identities.

```
Runas_Alias DBUSERS = postgres, mysql
```

### **6.3 Cmnd_Alias**

Groups commands.

```
Cmnd_Alias NGINX_STATUS = /usr/bin/systemctl status nginx
```

### **6.4 Applying an alias**

```
WEBADMINS ALL=(root) NGINX_STATUS
```

The alias definitions make larger policies easier to maintain.

Host aliases also exist and can be used when policy differs between machines.

Do not copy policy examples blindly into a production sudoers file. Confirm that the command paths and intended authorization are correct.

## **7. Editing sudo Policy Safely**

Critical administrative rule

Never casually edit `/etc/sudoers` with an ordinary text editor.

Incorrect syntax can prevent users from using sudo.

Use:

```
sudo visudo
```

`visudo` opens the policy file through a controlled editing workflow and validates syntax before accepting the change.

### **7.1 Why&#x20;**`visudo`**?**

It provides protections such as:

- Syntax validation.
- Editing safeguards.
- File locking to reduce conflicting changes.
- Warnings about malformed policy.

### **7.2 Edit a separate policy file**

Ubuntu commonly includes files from:

```
/etc/sudoers.d/
```

Use:

```
sudo visudo -f /etc/sudoers.d/webadmins
```

This lets you edit a separate policy file rather than modifying the main one.

The file should have appropriately restrictive permissions. A typical sudoers file uses mode `0440`.

For an illustrative policy file:

```
# Allow web administrators to inspect nginx status
%webadmins ALL=(root) /usr/bin/systemctl status nginx
```

This is an example to understand the format. It is not a recommendation to grant a real group access without evaluating the implications of the allowed command.

### **7.3 Validate the complete policy**

```
sudo visudo -c
```

This checks the sudoers configuration for syntax errors.

Validate a specific file:

```
sudo visudo -cf /etc/sudoers.d/webadmins
```

If you have not created that file, the command will report that it cannot find it.

## **8. Passwordless sudo — NOPASSWD**

A sudo policy can allow a command without prompting for the user's password.

Example:

```
alice ALL=(root) NOPASSWD: /usr/bin/systemctl status nginx
```

The tag is:

```
NOPASSWD:
```

This can be useful for narrowly scoped automation.

But there are risks:

- A stolen user account can execute the permitted operations immediately.
- Broad passwordless rules can effectively grant root.
- A permitted command may expose a shell or execute arbitrary code through its options or configuration.

Avoid rules such as:

```
alice ALL=(ALL) NOPASSWD: ALL
```

unless there is an exceptional, explicitly understood administrative reason.

A service account with carefully scoped access may be more appropriate than giving an interactive user broad passwordless root privileges.

### **The opposite tag: PASSWD**

The `PASSWD:` tag can require authentication for matching commands, subject to the user's wider policy and sudo configuration.

Policy order and matching rules can affect the final result, so always verify the effective policy with:

```
sudo -l
```

## **9. Sudo and Protected File Editing**

A common beginner mistake is:

```
sudo echo "hello" > /etc/example.conf
```

Why can this fail?

Because the shell performs the redirection before running the privileged command.

The shell tries to open `/etc/example.conf` using the current user's privileges.

Use:

```
echo "hello" | sudo tee /etc/example.conf
```

Here:

- `echo` runs as the normal user.
- `tee` runs as root.
- `tee` opens the protected file.

For interactive editing, use:

```
sudoedit /etc/example.conf
```

`sudoedit` is preferable to launching an arbitrary text editor as root because it edits a temporary copy and copies the updated result into place after authorization checks.

It is commonly useful when editing application configuration.

## **10. Environment and PATH Security**

Sudo often applies a controlled execution environment.

One important setting is `secure_path`.

It may define a restricted PATH used for privileged command execution.

Inspect the effective policy:

```
sudo -l
```

And inspect sudoers Defaults in the configuration:

```
sudo grep -R "secure_path\|env_reset" /etc/sudoers /etc/sudoers.d 2>/dev/null
```

Common settings include:

| Setting             | Purpose                                                    |
| ------------------- | ---------------------------------------------------------- |
| `env_reset`         | Restricts which environment variables are preserved        |
| `secure_path`       | Controls the PATH used for sudo commands                   |
| `use_pty`           | Uses a pseudo-terminal for command execution where enabled |
| `timestamp_timeout` | Controls how long sudo authentication can be reused        |

The exact defaults vary by distribution and configuration.

Why does this matter?

Imagine a user creates a malicious executable named `systemctl` inside a directory they control.

If a privileged command runs by resolving `systemctl` through an unsafe PATH, it could execute the wrong program.

Using controlled command paths and a secure execution environment helps reduce such risks.

## **11. Practical Demonstration A — Inspect Sudo Access**

Works in WSL2 Ubuntu

### **Step 1 — Identify your current account**

```
whoami
id
```

### **Step 2 — Inspect your sudo authorization**

```
sudo -l
```

This displays the effective permissions available to the current user.

### **Step 3 — Check whether the current user belongs to the administrative group**

```
getent group sudo
```

Typical Ubuntu installations use the `sudo` group for administrative authorization.

### **Step 4 — Inspect the policy file**

```
sudo less /etc/sudoers
```

Locate the group rule, commonly:

```
%sudo ALL=(ALL:ALL) ALL
```

### **Step 5 — Validate the policy**

```
sudo visudo -c
```

Expected successful validation resembles:

```
/etc/sudoers: parsed OK
```

The system may also report validation of included files.

Do not change the current account's sudo membership as part of this lesson.

## **12. Practical Demonstration B — Validate a Sudoers Rule Without Installing It**

We will create a temporary policy file for syntax checking.

This lets us learn `visudo` safely without changing real administrative access.

### **Step 1 — Create a temporary file**

```
mkdir -p ~/linux-learning/lab-15-sudo
cd ~/linux-learning/lab-15-sudo
```

Create a sample rule:

```
cat > sample-sudoers <<'EOF'
# Example policy for syntax validation only
User_Alias APP_OPERATORS = alice, bob
Cmnd_Alias APP_STATUS = /usr/bin/systemctl status nginx
APP_OPERATORS ALL=(root) APP_STATUS
EOF
```

This is an illustrative policy. It is not installed into `/etc/sudoers.d/`.

### **Step 2 — Validate syntax**

```
sudo visudo -cf sample-sudoers
```

The file should pass syntax checking if the syntax is valid.

### **Step 3 — Introduce a syntax error**

Make a copy:

```
cp sample-sudoers invalid-sudoers
```

Append an invalid line:

```
echo "invalid policy line" >> invalid-sudoers
```

Validate:

```
sudo visudo -cf invalid-sudoers
```

It should report a syntax error.

### **Step 4 — Compare and correct**

Inspect:

```
cat -n invalid-sudoers
```

Correct the invalid line or remove it:

```
sed -i '$d' invalid-sudoers
```

Validate again:

```
sudo visudo -cf invalid-sudoers
```

This demonstrates how administrators can validate policy before deploying it.

### **Step 5 — Clean up**

```
cd ~
rm -r -- ~/linux-learning/lab-15-sudo
```

No production sudo policy was changed during this exercise.

## **13. Practical Demonstration C — Understand Restricted Privilege Delegation**

Imagine that an application operator should inspect Nginx status but should not receive general root privileges.

A conceptual policy could be:

```
%webadmins ALL=(root) /usr/bin/systemctl status nginx
```

An administrator would need to:

1. Verify the exact command path.
2. Verify that the intended users are members of the correct group.
3. Inspect whether the permitted command can invoke other privileged functionality.
4. Install the policy using `visudo`.
5. Validate with `visudo -c`.
6. Test the effective authorization using `sudo -l -U username`.

Do not grant `restart`, `edit`, `shell` or unrestricted command access without reviewing the security implications.

### **Why command permissions need careful review**

Some administrative commands offer interactive functionality or can execute other programs.

A rule that appears to authorize one simple tool can accidentally grant much broader access.

For example, editors, interpreters, package managers and scripting tools can sometimes be used to execute arbitrary commands.

This is why command restrictions must consider the entire behavior of the permitted executable, not just its filename.

## **14. Sudo Audit and Logs**

Sudo can produce security-relevant logs.

Depending on the distribution and logging configuration, examine:

```
sudo journalctl -b | grep sudo
```

On Ubuntu systems that maintain traditional authentication logs:

```
sudo grep sudo /var/log/auth.log
```

Not every WSL installation has the same logging infrastructure enabled.

### **What should administrators monitor?**

- Successful sudo command execution.
- Failed authentication attempts.
- Changes to sudoers.
- Unexpected privilege escalation.
- Changes in administrative group membership.
- Use of passwordless sudo.

In production, these events are useful for security auditing and incident investigation.

## **15. Troubleshooting sudo**

| Problem                                   | Possible explanation                                                            | Diagnostic                                   |
| ----------------------------------------- | ------------------------------------------------------------------------------- | -------------------------------------------- |
| User is not allowed to run sudo           | Missing sudoers rule or group membership                                        | `sudo -l`, `id`                              |
| `sudo: command not found`                 | Sudo package missing or PATH issue                                              | `command -v sudo`                            |
| Authentication failure                    | Incorrect password or authentication configuration                              | Recheck account authentication               |
| Sudoers syntax error                      | Invalid policy file                                                             | `sudo visudo -c`                             |
| Rule is ignored                           | Wrong include path, file permissions or rule mismatch                           | Inspect `/etc/sudoers` and `/etc/sudoers.d/` |
| Command is not found under sudo           | Different secure PATH                                                           | `sudo -l`, inspect `secure_path`             |
| Permission denied while redirecting       | Shell performed redirection without elevated privileges                         | Use `sudo tee` or `sudoedit`                 |
| User still has access after group removal | Existing session may have old group credentials or another policy grants access | Start a new session and inspect `sudo -l`    |

### **Emergency recovery considerations**

Never deliberately break sudoers syntax on your only administrative account.

If a system's sudo configuration becomes invalid, recovery depends on the environment.

A conventional server may require console access or rescue mode. In WSL, recovery mechanisms are different, but do not assume you can always repair a broken policy from the same unprivileged session.

The safest approach is prevention:

- Use `visudo`.
- Validate changes.
- Preserve a working administrative session while testing.
- Avoid replacing the entire policy file.
- Keep backups of important policy files before making production changes.

## **16. Advanced Notes**

### **16.1&#x20;**`sudo`**&#x20;vs&#x20;**`su`

| Command                 | Purpose                                     |
| ----------------------- | ------------------------------------------- |
| `sudo command`          | Run one command as another user             |
| `sudo -i`               | Start a root login shell                    |
| `su - alice`            | Switch to Alice using her login environment |
| `sudo -u alice command` | Run a command as Alice                      |

`sudo` normally authenticates the invoking user, while `su` commonly authenticates using the target user's password, depending on configuration.

### **16.2 Root is not the only target identity**

A controlled sudo rule may permit an administrator to execute a command as a service account:

```
sudo -u postgres psql
```

This can be more appropriate than running all database administration commands as root.

### **16.3 Sudo does not make a dangerous command safe**

The following command is still destructive:

```
sudo rm -r /important/path
```

Sudo only changes the authorization context. It does not understand whether the command is a good idea.

### **16.4 WSL and sudo**

Ubuntu under WSL supports normal sudoers mechanisms.

Some environment-specific differences remain:

- WSL may have different login-session and service behavior from a full server.
- `systemctl` commands depend on whether systemd is enabled and available.
- Logging may differ from a traditional Ubuntu server.
- The account that launches WSL may have broad sudo privileges by default.

Our exercises validate sudo policy without changing the actual administrative configuration.

## **17. Real-World Production Scenario — Least-Privilege Administration**

Imagine a production hosting environment.

```
Production Linux server
│
├── sysadmin
│   └── Full administrative privileges
│
├── developer
│   └── Application deployment tasks
│
├── operator
│   └── Limited service inspection/restart tasks
│
└── postgres
    └── Database service identity
```

A sensible access design separates the roles.

| Role                 | Example access                                 |
| -------------------- | ---------------------------------------------- |
| System administrator | Full administrative operations                 |
| Developer            | Application files and deployment workflow      |
| Operator             | Approved service operations                    |
| Database service     | Database files and service-specific operations |

The objective is not simply to make administration convenient.

The objective is to reduce the number of identities that can perform unrestricted privileged operations.

That reduces the blast radius of compromised accounts and accidental mistakes.

## **18. Teaching Summary**

**Topic 06 — sudo key concepts**

- `sudo` runs authorized commands with elevated privileges.
- `sudo -l` lists effective permissions.
- `/etc/sudoers` defines sudo policy.
- `/etc/sudoers.d/` commonly holds additional policy files.
- `visudo` safely edits sudoers files and validates syntax.
- `sudo -u` runs commands as another identity.
- `sudo -i` starts a root login shell.
- `sudoedit` safely edits protected files.
- `NOPASSWD` allows specified commands without password prompts.
- Restrict privileges using least privilege.
- A sudo rule must be reviewed for indirect command execution and privilege escalation risks.
