Part 1 — Introduction: How Linux organizes everything
1.1 Start with a simple problem
Imagine you are building a computer operating system.

You have thousands of files:
- Applications.
- Configuration files.
- Libraries.
- User documents.
- System logs.
- Device information.
- Temporary files.
- Runtime information.
- Kernel information.
- Database files.
- Application data.
Now imagine putting all those files into a single folder.

You would quickly encounter problems:
- Application files would mix with user documents.
- Temporary files would mix with permanent data.
- Configuration files would be difficult to locate.
- System logs would become difficult to manage.
- Administrators would not know where software should store its data.
- Backup and recovery would become complicated.
Linux solves this organizational problem through a structured filesystem hierarchy.

A filesystem hierarchy defines how files and directories are organized and where different categories of information should live.

Linux follows established Unix filesystem conventions, particularly the Filesystem Hierarchy Standard (FHS).

The FHS defines guidelines for placing files and directories so that software, administrators and system tools can predict where things belong. The current published FHS specification is Version 3.0. 

specifications.freedesktop.org+1

1.2 The most important concept: Linux has one unified directory tree
Windows users are accustomed to seeing drives:
C:\
D:\
E:\


Each drive has its own drive letter and directory tree.

Linux works differently.

Linux exposes filesystems through one unified directory hierarchy.

The entire tree starts at:
/


This is called the root directory.

Everything else exists underneath it, either as an ordinary directory or as a mount point connected to another filesystem.

For example:
/
├── home
├── etc
├── usr
├── var
├── tmp
└── dev


All these paths belong to the same overarching namespace.

A directory does not need its own drive letter.
Windows versus Linux
Windows filesystem model
C:\

Windows operating system

Windows · Program Files · Users

D:\

Another drive

Projects · Backups · Media

E:\

Another drive



Linux filesystem model
/

One unified root directory

/home


/etc


/usr


/var


/tmp


/mnt



Different storage devices can be attached at directories within this same tree.


The Linux approach allows different storage devices and filesystems to appear at specific locations within the same directory hierarchy.

For example, a production server might have:
/
├── home       → user storage
├── var        → application state and logs
├── boot       → boot-related files
└── data       → separate mounted storage


Even if /data resides on a completely different physical disk, users access it through the same unified namespace.

This operation is called mounting, which we will examine in depth in Module 05.
1.3 What exactly is /?
The symbol / represents the root of the filesystem namespace.

It is the highest directory in the Linux directory hierarchy.

Examples:
/etc
/home
/usr
/var
/tmp
/dev


All these paths begin from /.

Important distinction:
- / is the filesystem root directory.
- /root is normally the home directory of the Linux root user.
- /home contains ordinary user home directories.
These three things are not interchangeable.

For example:
/
├── root
└── home
    ├── alice
    └── bob


The administrator account named root normally has:
/root


A regular user named alice might have:
/home/alice


This distinction becomes especially important when we study users and permissions.
1.4 What is a filesystem?
A filesystem is the mechanism and data structure used to organize and manage files on a storage medium or through a filesystem interface.

It handles concepts such as:
- File contents.
- Directory entries.
- Metadata.
- Permissions.
- File ownership.
- Timestamps.
- Storage allocation.
- Directory structures.
Examples of Linux filesystems include:
Filesystem	Common use
ext4	General-purpose Linux storage
XFS	Enterprise and server storage
Btrfs	Linux filesystem with snapshots and advanced features
tmpfs	Temporary filesystem backed by memory and possibly swap
vfat	FAT-compatible filesystems
NFS	Network filesystem

Do not confuse a filesystem with a filesystem hierarchy.

A filesystem is how data is managed and represented. The hierarchy is how locations are organized and exposed through paths.

For example:
ext4 filesystem
       |
       v
Mounted at /
       |
       v
Contains Linux directories
       |
       +-- /etc
       +-- /home
       +-- /usr
       +-- /var


A separate ext4 filesystem could also be mounted at /home, while the rest of the hierarchy remains available through the root filesystem.
1.5 Why does the filesystem hierarchy matter?
Imagine an application running on a cloud server.

Its components might be distributed like this:
Application executable:
    /usr/bin/myapp

Configuration:
    /etc/myapp/

Application persistent data:
    /var/lib/myapp/

Logs:
    /var/log/myapp/

Temporary files:
    /tmp/myapp/

Runtime socket:
    /run/myapp/


Each directory has a purpose.

If an application fails, an administrator can investigate the relevant location instead of searching the entire machine randomly.

Consider these examples:
Problem	Relevant directory
Application configuration is incorrect	/etc
Server disk is filling with logs	/var/log
Application cannot find its executable	/usr/bin or another executable location
Application has lost its persistent state	/var/lib
Temporary files are consuming storage	/tmp
Service cannot access its runtime socket	/run
Device or kernel information is needed	/dev, /proc, /sys
User cannot find personal files	/home

The filesystem hierarchy is therefore not just organization. It is an operational map of a Linux machine.

Part 3 — Understanding the major directories in depth
This is the most important part of the lesson.

We will examine each directory, its purpose, examples of files that belong there, how Linux uses it, and what an administrator investigates when something goes wrong.
3.1 / — The root directory
Filesystem root
Foundational

The root directory is the starting point of the entire Linux filesystem hierarchy.

Every ordinary directory and file is reachable underneath it.

Examples:
/
/etc
/home
/usr
/var
/tmp


What is its responsibility?
The root filesystem must contain enough essential files for a Linux system to start, operate sufficiently, and recover or repair itself.

The FHS describes this as one of the root filesystem's central responsibilities. 

specifications.freedesktop.org+1

How does Linux use it?
When Linux starts, the operating system needs an accessible root filesystem containing essential resources.

The kernel and initial userspace environment establish access to the root filesystem, after which the system can access other mounted filesystems.

For a typical Linux server:
/
├── boot
├── etc
├── home
├── usr
└── var


The root filesystem might contain everything, or individual directories might be separate mounted filesystems.

For example:
Filesystem A → /
Filesystem B → /home
Filesystem C → /var
Filesystem D → /data


The administrator sees one directory tree even though the data comes from multiple storage locations.
Production scenario
Suppose the root filesystem runs out of storage.

Even if a machine has another large storage disk, the operating system might experience failures if essential directories remain on the full root filesystem.

Possible symptoms:
- Applications cannot create temporary files.
- Services fail to write logs.
- Package installations fail.
- System updates cannot complete.
- Programs cannot create sockets or runtime files.
An experienced administrator investigates which mounted filesystem is full instead of simply assuming the physical disk is full.

We will learn the actual storage diagnostic workflow in Module 05.

3.2 /etc — System configuration
System configuration
Critical directory

What is /etc?
/etc contains system-wide configuration files.

These files control how applications, services and operating-system components behave.

Think of /etc as the configuration center of a Linux machine.

Examples:
/etc
├── hostname
├── hosts
├── passwd
├── group
├── fstab
├── ssh
├── apt
├── systemd
└── ...


Why does Linux need /etc?
Applications need configurable behavior.

For example, a web server might need to know:
- Which port to listen on.
- Which directory contains website files.
- Which hostname to serve.
- Which TLS certificate to use.
- Where to write logs.
- Which users or groups it should operate under.
Instead of hardcoding everything inside application executables, Linux software commonly uses configuration files.

The application reads those files when it starts or reloads its configuration.

The FHS defines /etc as the location for host-specific system configuration. 

specifications.freedesktop.org+1

Important files inside /etc
A. /etc/os-release
Identifies the operating system.
cat /etc/os-release


Example:
NAME="Ubuntu"
ID=ubuntu
VERSION_ID="24.04"


The exact output depends on the installed distribution.
B. /etc/hostname
Contains the system's configured hostname.

Inspect:
cat /etc/hostname


Example:
learning-machine


The hostname is the human-readable identity assigned to the machine.
C. /etc/hosts
Provides a local hostname-to-IP-address mapping.

Example:
127.0.0.1 localhost
127.0.1.1 learning-machine


Inspect:
cat /etc/hosts


Why is this useful?

Suppose an application tries to resolve:
my-local-app


A matching entry in /etc/hosts can provide a local address without needing a DNS server.

DNS and hostname resolution will be explored further in Module 06.
D. /etc/passwd
Contains account records.

Inspect:
cat /etc/passwd


Representative entry:
alice:x:1000:1000:Alice:/home/alice:/bin/bash


We will examine all seven fields in the Users and Permissions module.

For now, understand that this is part of the Linux user account database.
E. /etc/shadow
Contains password-related authentication data, including password hashes and account aging information.
Sensitive file
Do not use cat /etc/shadow as a beginner demonstration.

Inspect its permissions safely:
ls -l /etc/shadow


A typical Linux system restricts access to this file because its contents are security-sensitive.
F. /etc/fstab
The filesystem table.

It describes filesystems that should be mounted through the system's mount configuration.

Inspect:
cat /etc/fstab


An illustrative entry:
UUID=example-uuid /data ext4 defaults 0 2


Conceptually, it describes:
Field	Meaning
UUID	Filesystem identifier
/data	Mount location
ext4	Filesystem type
defaults	Mount options
0	Dump-related setting
2	Traditional filesystem check ordering

We will revisit this file when we study storage and mounting.
G. /etc/ssh/
Contains SSH server and client configuration, depending on which SSH components are installed.

An important example:
/etc/ssh/sshd_config


This is commonly used to configure the SSH server.

We will explore SSH in Module 02.
H. /etc/apt/
Contains APT configuration and repository source definitions on Ubuntu and Debian.

For example:
/etc/apt/sources.list.d/


Modern Ubuntu releases commonly use files with the .sources extension here.
I. /etc/systemd/
Contains systemd configuration files and unit configuration locations where systemd is installed.

Example:
/etc/systemd/system/


This directory is important when administrators create custom services or override existing service settings.

We will study it in Module 03.
How applications use /etc
Consider a web application.
Administrator edits configuration
              |
              v
/etc/myapp/myapp.conf
              |
              v
Application starts
              |
              v
Application reads configuration
              |
              v
Application applies settings
              |
              v
Application runs


The operating system does not automatically interpret every file in /etc.

The application or service that owns a particular configuration file is responsible for reading and using it.
What should not normally go into /etc?
Do not use /etc as a general storage location for:
- Application logs.
- User documents.
- Database files.
- Uploaded files.
- Temporary exports.
- Large application-generated datasets.
The directory is intended for configuration.
Production scenario: Configuration failure
A web application stops starting after a configuration change.

An administrator investigates:
ls -la /etc/myapp/


Then inspects the configuration:
cat /etc/myapp/myapp.conf


The administrator compares the modified configuration against the expected format, corrects the invalid setting and verifies the application.

The exact service verification commands depend on the application.

Key lesson: When an application behaves incorrectly because of its settings, /etc is one of the first places to investigate.

3.3 /home — Ordinary user home directories
User data

What is /home?
/home contains personal home directories belonging to ordinary Linux users.

Example:
/home
├── alice
├── bob
└── student


A user named alice might have:
/home/alice


This directory is commonly abbreviated using the tilde character:
~


For example:
cd ~


This changes the current directory to the current user's home directory.

For our learner, the home directory may be:
/home/student


What lives inside a home directory?
Typical contents:
/home/student
├── Documents
├── Downloads
├── Projects
├── .bashrc
├── .profile
├── .ssh
└── .config


The contents depend on the distribution, installed applications and user.

Some important examples:
Path	Purpose
~/.bashrc	Bash interactive non-login shell configuration
~/.profile	Login environment initialization on many systems
~/.ssh/	User SSH keys and configuration
~/.config/	Per-user application configuration
~/Projects/	User-created projects

We will study shell startup files in Topic 07.
How does Linux use /home?
When a user signs into Linux, the operating environment usually assigns that user's home directory.

It is available through the environment variable:
echo "$HOME"


Representative output:
/home/student


Applications often use the home directory for:
- Personal configuration.
- Developer projects.
- SSH keys.
- Command history.
- Personal files.
- Application preferences.
Production scenario: Application cannot access a user's files
Suppose an application tries to read:
/home/alice/project/config.json


But the application process runs as another user.

Even if the file exists, the process might not have permission to access it.

The administrator must investigate ownership and permissions.

We will cover the actual permission model in Module 02.
Important distinction
/home is intended for ordinary user accounts.

The root administrator's home directory is normally:
/root



3.4 /root — Home directory of the root user
Root administrator's home

This directory causes confusion because Linux uses the word root for two different concepts.

Concept 1: Filesystem root
/


The starting point of the filesystem hierarchy.

Concept 2: Root user's home directory
/root


The home directory of the privileged Linux account named root.

Example:
/
├── root
├── home
│   ├── alice
│   └── bob
├── etc
└── var


Why does /root exist separately?
The root account has administrative privileges.

Its configuration and personal files should not depend on ordinary users' home directories.

The /root directory provides the root account with its own home location.
How can you inspect it?
ls -ld /root


This shows directory metadata without listing its contents.

Depending on the learner's account and permissions, reading the contents may be restricted.
Advanced note
Linux commonly uses a special user identity:
root
UID 0


This is the primary traditional superuser identity.

We will learn why this account has special privileges in the Users and Permissions module.

Important: Do not use the root account for every ordinary activity. The principle of least privilege will be central to our administration training.

3.5 /usr — Installed software and shared resources
Software hierarchy
Very important

What is /usr?
/usr is one of the most important directories in Linux.

It contains a large part of the software and supporting resources installed on the operating system.

Examples:
/usr
├── bin
├── sbin
├── lib
├── libexec
├── local
├── share
├── include
└── src


A beginner often assumes /usr means the directory containing user documents.

That is incorrect.

The directory is a historical Unix convention and primarily holds system software, libraries and shared data.

The FHS defines /usr as a major secondary software hierarchy. 

specifications.freedesktop.org+1

A. /usr/bin
Contains most ordinary executable programs.

Examples may include:
/usr/bin/ls
/usr/bin/cat
/usr/bin/grep
/usr/bin/python3
/usr/bin/curl


Inspect:
ls -ld /usr/bin


Locate a program:
command -v python3


On many Ubuntu systems, the result is:
/usr/bin/python3


The exact executable location can differ.
What does an executable mean?
An executable is a file that the operating system can run as a program, subject to appropriate permissions and execution rules.

For example, when Bash executes an external utility such as grep, it must locate the relevant executable.

The shell commonly searches directories specified in the PATH environment variable.

We will study this mechanism in the Environment Variables topic.
B. /usr/sbin
Traditionally contains system administration programs that are not essential for the most minimal system-recovery environment.

The distinction between /usr/bin and /usr/sbin is less strict than it historically was.

Modern distributions may place many administrative executables in /usr/bin.

Do not assume that every command named somethingadmin must reside in /usr/sbin.
C. /usr/lib
Contains program libraries and supporting software files.

What is a library?

A software library is reusable code that programs can use rather than implementing every functionality themselves.

For example, an application might depend on:
- OpenSSL libraries.
- C standard libraries.
- Database client libraries.
- Runtime support libraries.
The operating system provides these libraries in standard locations.

A program may fail to start when an expected shared library is missing or incompatible.

That is one reason /usr/lib is operationally important.
D. /usr/share
Contains architecture-independent shared data.

Examples include:
/usr/share/man
/usr/share/doc
/usr/share/zoneinfo
/usr/share/applications


Consider:
/usr/share/man


This location contains many installed manual pages.

When you run:
man ls


The manual-page system can retrieve the documentation installed for ls.

Not every file in /usr/share is a manual page. It can contain translations, themes, documentation and other shared data.
E. /usr/local
This is particularly important for administrators and developers.

/usr/local is intended for software and data installed locally by the system administrator rather than supplied as part of the normal distribution-managed software hierarchy.

A common structure is:
/usr/local
├── bin
├── sbin
├── lib
├── etc
├── share
└── src


For example:
/usr/local/bin/my-tool


This might be a locally installed administration utility.
Why does /usr/local matter?
Imagine you install a custom internal utility.

You could place it under:
/usr/local/bin/


This separates it from programs supplied by the distribution.

It makes ownership and maintenance easier to understand.

It also reduces the chance that your custom application will conflict with a distribution-managed package at the same path.

However, this is a convention, not an absolute guarantee.
/usr/bin versus /usr/local/bin
Directory	Typical responsibility
/usr/bin	Distribution-managed executable programs
/usr/local/bin	Locally installed executable programs

Example:
/usr/bin/python3
/usr/local/bin/my-custom-script


Production scenario
An organization deploys an internal monitoring tool to all its Linux servers.

Rather than placing it randomly in /home/admin/Downloads, it installs the utility at:
/usr/local/bin/server-health


If that directory is on the user's PATH, administrators can execute:
server-health


This is more maintainable than relying on the location of an individual administrator's personal files.

3.6 /bin, /sbin and /lib
These directories deserve separate attention because their historical roles can confuse people using modern Ubuntu.
/bin
Historically, /bin contained essential commands needed to use and repair the system.

Examples included:
/bin/sh
/bin/ls
/bin/cat
/bin/mkdir


Modern Linux distributions increasingly use a design called merged-/usr.

In a merged-/usr environment, directories such as:
/bin
/sbin
/lib


may be symbolic links into /usr.

For example:
/bin -> usr/bin
/sbin -> usr/sbin
/lib -> usr/lib


This allows compatibility with older software while organizing the main software hierarchy under /usr.

The FHS explicitly allows required top-level directories to be symbolic links. 

Filesystem Hierarchy Standard+1

Inspect the actual environment:
ls -ld /bin /sbin /lib


The first character in the output can indicate a symbolic link.

For example:
lrwxrwxrwx ... /bin -> usr/bin


Do not assume every distribution uses this exact layout.
/sbin
Historically contained essential system administration commands.

Examples:
/sbin/fsck
/sbin/reboot
/sbin/init


Actual locations vary across modern distributions.

Some of these commands may now live in /usr/sbin or elsewhere.
/lib
Traditionally contains essential shared libraries required by core system executables.

It may also contain kernel-related modules in distribution-specific arrangements.

For example:
/lib/modules/


This location is associated with loadable kernel modules on many conventional Linux systems.
What is a shared library?
Suppose several programs need the same cryptographic functionality.

Instead of each program containing a completely separate copy of every cryptographic routine, they can dynamically link to a shared library.

This reduces duplication and allows shared functionality.

An executable may depend on several shared libraries.

A missing or incompatible dependency may prevent it from running.
Important safety note
Do not manually delete or replace files inside /bin, /sbin or /lib.

These are core software locations.

Incorrect changes can break important commands or the operating system itself.

3.7 /var — Variable data
Variable system and application data
Production-critical

What is /var?
/var stores data that changes while the operating system and applications run.

The word var comes from variable.

Unlike many files in /usr, which are installed software and relatively static data, /var holds information that changes during normal operation.

The FHS includes logs, cache data, application state and spool data within this hierarchy. 

specifications.freedesktop.org+1

Think of it this way:
/usr
  |
  +-- Installed programs and supporting files

/var
  |
  +-- Data produced or changed during operation


Important subdirectories inside /var
A. /var/log — System and application logs
Log files

Logs record events that occur in the operating system and applications.

Examples:
/var/log
├── syslog
├── auth.log
├── kern.log
└── apt


Exact files vary by distribution and logging configuration.

Inspect:
ls -lh /var/log


On Ubuntu systems using traditional rsyslog logging, common examples are:
File	Purpose
/var/log/syslog	General system messages
/var/log/auth.log	Authentication-related messages
/var/log/kern.log	Kernel-related messages
/var/log/apt/	APT package management logs

On systems where systemd-journald handles logging, logs may also be maintained in the journal rather than appearing as individual text files.

We will study journald in Module 03.
Why are logs important?
Suppose a web server stops working at 14:35.

An administrator needs evidence of what happened around that time.

The logs might show:
14:32 Application started
14:33 Database connection established
14:34 Configuration reload attempted
14:35 Application error


These are illustrative events.

Logs allow administrators to reconstruct events and identify causes instead of guessing.

Production reality: /var/log is one of the first locations investigated during many incident-response and troubleshooting situations.
B. /var/lib — Persistent application state
This directory is especially important.

/var/lib contains variable state associated with applications and system components.

For example:
/var/lib
├── dpkg
├── apt
├── systemd
└── ...


Possible application data might reside under:
/var/lib/postgresql/
/var/lib/mysql/
/var/lib/docker/


These are examples; actual paths depend on the distribution, application and configuration.
What is persistent application state?
Suppose you run a database.

The database needs to remember:
- Stored records.
- Indexes.
- Internal metadata.
- Transaction state.
- Other database-managed information.
That is persistent application state.

Unlike temporary data, it must survive normal reboots.

Administrators must understand exactly where an application stores that data before planning backups, upgrades or migrations.

Very important: Do not assume every database or application stores all its data in /var/lib. Always inspect its actual configuration.
C. /var/cache — Regenerable cache data
A cache stores information that can often be regenerated.

For example:
- Downloaded package metadata.
- Application cache entries.
- Generated thumbnails.
- Temporary optimized content.
A cache is not necessarily unimportant, but it is usually different from the application's authoritative persistent data.

This distinction matters when managing disk space.

Removing a cache may cause an application to regenerate information and use more resources later.

Never assume every cache directory can be safely deleted while the application is running.
D. /var/tmp — Longer-lived temporary files
This directory stores temporary data that is generally expected to survive longer than files in /tmp.

A useful distinction:
Directory	Intended role
/tmp	Short-lived temporary files
/var/tmp	Temporary files that may need to persist longer

The exact cleanup behavior depends on distribution policies and system configuration.

Neither directory should be treated as permanent application storage.
E. /var/spool — Queued work
A spool is a location where work waits until it can be processed.

Examples:
- Print jobs.
- Scheduled tasks.
- Mail queues.
- Other queued application work.
For example:
/var/spool/


An application may place a task into a queue, then another process consumes and processes it.

This concept becomes important when studying background services and scheduling.
F. /var/backups
Some distributions and applications use this location for system backup data.

It may contain automatically generated backups of selected configuration or package-management information.

It is not a universal destination for every server backup.
Production scenario: Server disk fills unexpectedly
An administrator receives an alert:
Root filesystem usage: 96%


Instead of immediately deleting random files, the administrator investigates:
df -hT


Then:
du -sh /var/log


And:
du -sh /var/lib


Suppose the administrator finds that logs occupy a significant amount of space.

The next steps are:
1. Determine which log files are growing.
2. Identify which service is generating them.
3. Investigate why the messages are repeating.
4. Correct the underlying service problem.
5. Apply an appropriate log retention or rotation policy.
6. Verify that storage usage is returning to a safe level.
Deleting logs without finding the cause may only hide the problem temporarily.

Also, du and df can report different usage because they inspect different aspects of filesystem allocation. We will explore this during the storage module.

3.8 /tmp — Temporary files
Temporary working storage

What is /tmp?
/tmp is a location for temporary files.

Programs often need temporary storage while performing operations.

Examples:
- Intermediate build artifacts.
- Temporary exports.
- Application scratch files.
- Short-lived processing data.
- Temporary communication files.
Example:
/tmp
├── temporary-report.txt
├── build-cache
└── application-session-data


These are illustrative names.
Why does Linux need a temporary directory?
Imagine a program processes a large file.

It might:
1. Read the original file.
2. Generate an intermediate result.
3. Modify the result.
4. Complete the operation.
5. Remove the intermediate file.
The program needs somewhere to store that temporary information.

/tmp provides a common location.
Important behavior
Files in /tmp are not guaranteed to remain permanently.

A distribution may clean them during boot or through scheduled cleanup policies.

On some systems, /tmp is mounted using tmpfs, which means it is backed by memory and potentially swap rather than being an ordinary persistent disk filesystem.

On other systems, it may reside on regular storage.

Inspect:
findmnt -T /tmp


This shows the filesystem and mount information for /tmp.
Security consideration
Temporary files can create security problems when programs:
- Use predictable filenames.
- Store sensitive information without appropriate protection.
- Leave secrets behind.
- Follow attacker-controlled symbolic links incorrectly.
- Allow other users to interfere with temporary files.
A safer approach for scripts is often to use mktemp.

Example:
temp_file=$(mktemp)


This asks the system to create a uniquely named temporary file.

We will study safe scripting later.

Never place critical permanent data in /tmp.

3.9 /run — Runtime information
Runtime state

What is /run?
/run stores runtime information associated with the currently operating system instance.

Examples:
- Process identification files.
- Unix domain sockets.
- Service runtime state.
- Lock information.
- Other transient system data.
Example:
/run
├── lock
├── systemd
├── user
└── ...


The actual contents vary considerably.
Why does it exist?
Applications and services often need to coordinate while they are running.

For example, a service may need to create a socket file so other programs can communicate with it.

A process manager may need runtime information about currently managed processes.

/run provides a standard location for this kind of state.
Difference between /run and /var
This distinction is important.
/run	/var
Runtime state	Variable system and application data
Generally transient	Can contain persistent data
Active service information	Application state, logs and caches
Usually recreated during system startup	Contents persist according to the filesystem and application policies

For example:
/run/myapp/


Might contain a runtime socket.

Meanwhile:
/var/lib/myapp/


Might contain persistent application state.

These locations serve different purposes.
Production scenario
A service fails because another process cannot connect to its Unix domain socket.

The administrator might inspect:
ls -la /run/


And the application's runtime directory:
ls -la /run/myapp/


The objective is to determine whether:
- The expected socket exists.
- The service started.
- The runtime directory exists.
- The process has appropriate access.
We will cover the service-management side in Module 03.

3.10 /dev — Device files
Device interfaces

This is one of the most interesting parts of Linux.
What is /dev?
/dev contains device nodes and special files that expose interfaces to devices and certain kernel facilities.

Examples:
/dev
├── null
├── zero
├── random
├── urandom
├── tty
└── ...


On a conventional Linux machine, it may also contain device nodes corresponding to hardware devices such as disks and terminals.
Why does Linux represent devices as files?
Unix-derived systems follow the philosophy of providing common interfaces for interacting with different resources.

This allows programs to interact with many device interfaces using familiar file operations.

However, not everything in Linux is literally an ordinary file stored on disk.

Device nodes represent special kernel-managed interfaces.
Important devices
A. /dev/null

This is a data-discarding device.

Anything written to it is discarded.

Example:
echo "This will not be displayed" > /dev/null


The command writes its output to /dev/null instead of the terminal.

Why is this useful?

Suppose a script produces unimportant output, but the administrator wants to hide it.

Output can be redirected to /dev/null.

We will study redirection in Topic 05.

B. /dev/zero

Provides a stream of zero-valued bytes.

It is commonly used in controlled storage and testing operations.

Do not use it to generate large files on the learner's real filesystem.

C. /dev/random and /dev/urandom

Provide interfaces to the kernel's random-number generation system.

They are used by applications requiring random data.

The modern Linux kernel uses a cryptographically secure random-number generator and the two interfaces have evolved over time; do not assume the historical behavior of /dev/random on older systems applies to current Linux.

D. /dev/tty

Refers to the controlling terminal of the current process, when one exists.

This is useful for terminal-oriented interactions.
How does it work internally?
Consider a program writing to /dev/null.
Application
    |
    v
Open /dev/null
    |
    v
Kernel device handling
    |
    v
Write operation
    |
    v
Data discarded


The program uses a file-like interface, but the kernel handles the operation according to the special device's implementation.

The actual hardware is not necessarily involved.
WSL limitations
WSL provides Linux device interfaces, but it does not expose unrestricted access to every physical device on the Windows machine.

Some devices are virtualized or provided through WSL integration.

Do not assume that seeing a device under /dev means Linux has direct unrestricted control over the corresponding Windows hardware.

3.11 /proc — Process and kernel information
Process information
Important for diagnostics

What is /proc?
/proc is a virtual filesystem known as procfs.

It exposes information about processes and the operating system's running state.

Unlike an ordinary filesystem containing persistent files stored on a disk, much of the information under /proc is generated dynamically by the kernel.

The Linux manual describes /proc as an interface providing access to kernel data structures and process information. 

Linux manual page+1

What is a virtual filesystem?
A virtual filesystem provides a filesystem-like interface to data that does not necessarily exist as normal files on physical storage.

For example:
cat /proc/uptime


The command reads information exposed by the kernel.

It is not reading a normal uptime document saved to disk.
Important locations inside /proc
A. /proc/cpuinfo

Information about processors visible to the Linux environment.
cat /proc/cpuinfo


Output can include:
- Processor identifiers.
- CPU architecture information.
- Processor features.
- Virtual CPU details.
In WSL, the information represents the virtualized CPU environment rather than an unrestricted hardware inventory.

B. /proc/meminfo

Information about memory usage and memory management.
cat /proc/meminfo


Example fields:
MemTotal
MemFree
MemAvailable
Buffers
Cached
SwapTotal
SwapFree


These fields help administrators investigate memory behavior.

We will study them thoroughly in Stage 02.

C. /proc/uptime

Shows system uptime information.
cat /proc/uptime


It typically produces two numbers:
123456.78 234567.89


These are representative values.

The first describes elapsed time since the kernel started. The second reports accumulated idle time across CPUs, with details depending on the kernel interface.

D. /proc/self/

Provides information associated with the process accessing the interface.

For example:
cat /proc/self/status


This displays status information about the process used to read the file.

The PID-related directories under /proc are particularly important.

Example:
/proc/1/
/proc/100/
/proc/2500/


These directories represent processes using their process IDs.

A process ID, or PID, uniquely identifies a process within its PID namespace during its lifetime.
How does Linux use /proc?
The kernel exposes process-related and system-related information through procfs.

A monitoring utility can read that information without needing to develop its own kernel module.

For example:
top
  |
  v
Reads process and system information
  |
  v
/proc interfaces and other system interfaces
  |
  v
Kernel-provided information
  |
  v
Displays resource usage


This is one reason /proc is extremely important for Linux diagnostics.
Important warning: Not all /proc entries are read-only
Some files under:
/proc/sys/


expose configurable kernel parameters.

Changing values through these interfaces can alter runtime kernel behavior.

For this lesson, inspect information only.

Do not write arbitrary values into /proc.

3.12 /sys — Kernel devices and subsystem information
Kernel and device information

What is /sys?
/sys is another virtual filesystem.

It is provided by the kernel and is commonly associated with sysfs.

While /proc exposes broad process and kernel information, /sys provides a structured view of devices, drivers, kernel objects and system subsystems.

The Linux manual describes sysfs as an interface exposing information about kernel objects and the device model. 

Linux manual page+1

Examples
/sys
├── block
├── bus
├── class
├── devices
├── dev
├── firmware
├── kernel
└── module


Not every system has all of these locations populated.
A. /sys/class
Provides views organized by device class.

For example:
ls /sys/class/


Possible entries include:
block
net
tty


The exact list depends on the system.
B. /sys/class/net
Contains network-interface information.

Inspect:
ls /sys/class/net/


Representative output:
eth0
lo


These are examples; WSL network interface names can differ.
C. /sys/block
Provides information about block devices.

On a conventional Linux host, it can expose information about storage devices.

Inspect:
ls /sys/block/


WSL may expose a limited or virtualized view depending on the environment.
How is /sys different from /proc?
/proc	/sys
Process and kernel information	Device and kernel-object information
Process-specific directories	Device, bus and class hierarchy
Memory and uptime information	Interface and hardware attributes
Kernel information API	Kernel device-model API

Important security warning

For this lesson, read information only.

Never experiment with writes to /sys without first understanding the exact attribute and its effects.

3.13 /boot — Boot-related files
Operating system startup

What is /boot?
/boot contains files needed during a conventional Linux system boot.

Examples may include:
/boot
├── vmlinuz-...
├── initrd.img-...
├── config-...
└── grub/


Actual contents depend on the boot architecture and distribution.
What is the Linux kernel image?
The kernel image is the executable kernel that the boot process loads.

It contains the core Linux operating system code.
What is initramfs?
An initramfs is an initial temporary root filesystem used during early boot.

It contains tools and components needed to prepare the actual root filesystem and continue startup.

For example, it may contain storage drivers or utilities needed to access the system's real root filesystem.
What is GRUB?
GRUB is a widely used bootloader.

A bootloader helps load the operating system kernel.

On a conventional Linux installation, GRUB configuration and supporting files may be stored under locations such as:
/boot/grub/


Why is /boot important?
If a conventional Linux machine cannot find or load its kernel, the operating system may fail to boot.

If the bootloader configuration is damaged, startup can also fail.

An administrator may have to investigate bootloader configuration, kernel images and initramfs contents.
What about WSL?
This is an important environment difference.

WSL 2 does not perform the ordinary bare-metal Linux boot sequence using a guest GRUB bootloader.

Microsoft manages the Linux kernel used by WSL 2.

Therefore, seeing /boot in WSL does not mean the learner should experiment with GRUB, bootloader installation or kernel replacement.
WSL LIMITED
We will study the full boot process in Stage 03.

Filesystem attachment

What is /mnt?
/mnt is a traditional directory used as a temporary mount point for filesystems.

For example, suppose you connect a storage device to a Linux server.

Its filesystem might be mounted at:
/mnt/backup


Then files can be accessed through:
/mnt/backup/


The directory is part of the same unified Linux path structure.

Part 5 — How Linux actually sees the filesystem
We have examined what each directory contains. Now let's understand the underlying architecture.
5.1 A path is not necessarily a physical location
Consider:
/home/student/projects


It looks like a regular directory path.

However, its data might be stored on:
- The root filesystem.
- A separate SSD partition.
- A network filesystem.
- A mounted virtual disk.
The path itself does not reveal the underlying storage device.

This is one of the most important ideas in Linux.

A Linux path identifies a location in the filesystem namespace, not necessarily a direct location on a physical disk.
5.2 What is a mount point?
A mount point is a directory where a filesystem is attached to the main directory hierarchy.

Example:
Main filesystem
      |
      v
      /
      |
      +---- /etc
      |
      +---- /home
      |
      +---- /var
      |
      +---- /data  <---- Separate filesystem mounted here


Suppose the /data directory exists before mounting.

After another filesystem is mounted there, accessing /data shows the contents of that mounted filesystem.

The directory acts as the attachment point.

The underlying files that were previously visible at that location are hidden from the normal mounted view until the filesystem is unmounted.

This is an important operational detail.

Do not mount filesystems over important directories without understanding the consequences.
5.3 What is a virtual filesystem?
A virtual filesystem gives programs access to filesystem-like interfaces that may represent information rather than persistent disk files.

Linux uses several important virtual filesystem implementations.
Filesystem	Mount location	Purpose
procfs	/proc	Process and kernel information
sysfs	/sys	Devices and kernel objects
devtmpfs / dev filesystem	/dev	Device nodes
tmpfs	Various locations	Memory-backed temporary data

A virtual filesystem may present information as files and directories even when it is not storing those files as ordinary persistent disk objects.

This is why:
ls /proc


can display directories corresponding to currently running processes.

The kernel is exposing information through a filesystem interface.
5.4 What happens when you read /proc/meminfo?
Conceptually:
User runs:
cat /proc/meminfo
       |
       v
Bash starts cat
       |
       v
cat requests the file's contents
       |
       v
Kernel handles procfs access
       |
       v
Kernel provides memory information
       |
       v
cat writes output to the terminal


The contents are generated from kernel-maintained information.

They are not a regular memory report file stored permanently on the SSD.
5.5 How can you see mounted filesystems?
The command:
findmnt


displays mounted filesystem information in a tree-like layout.

To inspect the filesystem that contains the root directory:
findmnt -T /


To inspect /home:
findmnt -T /home


To inspect /proc:
findmnt -T /proc


The -T option identifies the filesystem containing the specified path.

Representative output may contain fields such as:
TARGET  SOURCE       FSTYPE OPTIONS
/       /dev/...     ext4   ...


In WSL, the root filesystem is typically backed by the distribution's virtual disk.

The actual source and filesystem information depend on the running environment.
5.6 How do you see filesystem capacity?
Run:
df -hT


Breakdown:
- df reports filesystem disk-space usage.
- -h shows human-readable sizes such as GB and MB.
- -T includes the filesystem type.
Representative output:
Filesystem     Type   Size  Used  Avail Use% Mounted on
/dev/...       ext4   250G   18G   220G   8% /
none           tmpfs   ...   ...    ...   ... /dev


The numbers and filesystem sources will vary.

Important columns:
Column	Meaning
Filesystem	Device or filesystem source
Type	Filesystem type
Size	Total reported capacity
Used	Used space
Avail	Available space
Use%	Percentage used
Mounted on	Location in the Linux hierarchy

This command is useful for identifying which mounted filesystem is approaching capacity.

We will study df and du in detail in Module 05.

7.3 Inspect directories with their child directories
Run:
ls /usr


Then:
ls /var


Then:
ls /etc


Explain to the learner:

7.4 Inspect the hierarchy using find
The find command searches directory trees.

For example:
find /usr -maxdepth 1 -type d


Breakdown:
- find searches files and directories.
- /usr is the starting location.
- -maxdepth 1 prevents traversal into child directories.
- -type d selects directories.
This provides a useful view of the top-level /usr structure.

For an even clearer output:
find /usr -maxdepth 2 -type d


This displays directories up to two levels below /usr.

Avoid running an unrestricted find / operation as an introductory exercise. It can traverse large virtual filesystems, generate permission errors and examine transient process interfaces.
7.5 Inspect symbolic links
On modern Ubuntu systems, some traditional directory names may be symbolic links.

Check:
ls -ld /bin /sbin /lib


Then:
readlink -f /bin


readlink reads symbolic-link information.

The -f option resolves the final canonical path, following the link.

For example, on a merged-/usr system:
/usr/bin


may be the resolved path.

This is a very useful administration technique because it reveals the actual filesystem structure rather than relying on an assumption.
7.6 Inspect a filesystem's type
Run:
df -hT /


This shows the filesystem containing /.

Then:
findmnt -T /


This identifies the mount supplying the root directory.

findmnt -T /proc

For /sys:
findmnt -T /sys


You should see sysfs.

The precise output depends on the WSL version and distribution configuration.
7.7 Inspect virtual filesystem information
Run these commands individually:
cat /proc/uptime


head -n 10 /proc/meminfo


ls /proc/self/


ls /sys/class/


ls /dev/


Now explain the difference:
- /proc exposes process and kernel information.
- /sys exposes structured device and kernel-subsystem information.
- /dev exposes device interfaces.
These three directories are not ordinary data directories.
7.8 Understand directory sizes
Run:

Breakdown:
- du estimates storage usage.
- -s displays a summary.
- -h displays human-readable sizes.
- /var/log specifies the directory.

But it should not unnecessarily overwrite:
- Database files.
- Customer uploads.
- Application configuration.
- Operational history.
Separating the responsibilities makes upgrades and recovery more predictable.

Consider:
Application update
      |
      v
Replace executable
      |
      v
Preserve configuration
      |
      v
Preserve persistent application state
      |
      v
Restart service
      |
      v
Verify application


This is the foundation of maintainable server deployments.
8.3 What about databases?
Suppose PostgreSQL is running on a Linux server.

Depending on the distribution and installation method, its database files might reside in a location such as:
/var/lib/postgresql/


The administrator must understand that these are not disposable cache files.

The files may contain valuable persistent database state.

Deleting or modifying them manually could destroy the database.

Normal database backup, recovery and maintenance procedures must be used.
8.4 Why separate storage for /var and /home?
A production Linux server may have several filesystems.

For example:
Filesystem 1: /
Filesystem 2: /home
Filesystem 3: /var
Filesystem 4: /data


There are operational reasons for this design.

Separate /home:

A user's large personal file collection is less likely to consume all root filesystem capacity.

Separate /var:

Application logs and mutable state can be controlled independently.

Separate /data:

Large application datasets can be stored separately from the operating-system installation.

However, separating every directory into its own partition adds administration complexity and must be designed around actual workload requirements.

It is not automatically beneficial for every machine.
8.5 Backup strategy and the filesystem hierarchy
A good administrator does not blindly back up every directory using the same policy.

Different locations have different operational meanings.
Location	Typical backup approach
/etc	Important configuration backup
/home	User-data backup
/var/lib	Application-consistent persistent state backup
/var/log	Retention and incident-evidence policy
/usr	Usually reproducible through package installation and deployment
/tmp	Generally excluded from routine permanent backups
/run	Generally excluded because it is transient
/proc	Not backed up as ordinary files
/sys	Not backed up as ordinary files
/dev	Device interfaces are recreated by the system

A critical warning:

Backing up a database's live data directory by simply copying files may produce an inconsistent backup.

The correct procedure depends on the database's backup mechanism, transaction state and filesystem snapshot support.

This is why understanding the role of a directory matters before writing backup scripts.

Part 9 — Troubleshooting through filesystem evidence
An advanced Linux administrator should know how to connect symptoms to filesystem locations.
9.1 Problem: The application cannot find its configuration
Symptom:
Configuration file not found


Investigation:
ls -la /etc/


Then inspect the relevant application directory:
ls -la /etc/myapp/


Check whether the expected file exists:
test -f /etc/myapp/config.yaml && echo "Configuration exists"


What does test -f do?
- test evaluates a condition.
- -f checks whether the supplied path exists as a regular file.
- && runs the next command only when the preceding command succeeds.
If the file exists, the investigation continues with permissions, ownership and application-specific configuration.

Do not assume that file existence means the application can read it.
9.2 Problem: Server disk space is running out
Symptom:
No space left on device


First inspect filesystem capacity:
df -hT


Then inspect relevant directory usage:
sudo du -xhd1 /var


Explanation:
- sudo executes the inspection with elevated privileges.
- du estimates directory storage usage.
- -x stays on the same filesystem rather than crossing filesystem boundaries.
- -h displays human-readable sizes.
- -d1 limits the directory depth to one level.
The learner might discover:
/var/log
/var/lib
/var/cache


are responsible for significant storage use.

Next, investigate the largest relevant subdirectory rather than deleting files immediately.

For example:
sudo du -ah /var/log | sort -h | tail -n 20


This lists large files and directory entries, sorted by reported size.

Caution: the command can be more expensive on very large directories and its output can include directory totals alongside file sizes. It is an investigation aid, not a definitive cleanup command.
9.3 Problem: A service's runtime socket is missing
Symptom:

An application reports that it cannot connect to a socket.

Inspect:
ls -la /run/


Then:
ls -la /run/myapp/


The administrator investigates:
- Is the application running?
- Does the runtime directory exist?
- Was the socket created?
- Did startup fail before creating it?
- Is another process responsible for the socket?
The correct fix depends on the process and its service configuration.

Manually creating a fake socket file will not fix the underlying application failure.
9.4 Problem: Executable exists but cannot be found
Symptom:
command not found


First inspect whether the executable exists.

Example:
ls -l /usr/local/bin/my-tool


Then inspect the executable lookup path:
echo "$PATH"


The PATH environment variable contains directories in which the shell searches for executable commands.

The executable might exist but reside in a directory not included in PATH.

This leads directly into Topic 06: Environment Variables.
9.5 Problem: Application works but cannot write data
The application starts successfully but cannot save uploaded files.

Possible application data directory:
/var/lib/myapp/


Inspect:
ls -ld /var/lib/myapp/


Then inspect the actual file or directory involved.

Possible causes include:
- Incorrect ownership.
- Insufficient write permissions.
- Read-only filesystem.
- Full disk.
- Application configured to use the wrong location.
- Security policy restrictions.
An important lesson:

The filesystem hierarchy helps locate the problem, but permissions, storage and security investigations determine the actual root cause.
9.6 Problem: /proc does not contain expected information
The administrator tries:
cat /proc/some-file


But receives:
No such file or directory


Possible causes:
- Incorrect filename.
- Expected kernel interface is unavailable.
- The relevant feature is unsupported.
- The environment is virtualized or restricted.
- A process-specific entry disappeared because the process exited.
The administrator should first inspect the actual contents:
ls /proc/


Do not assume every conventional Linux server exposes an identical /proc layout.
9.7 Problem: A file appears missing after mounting storage
Imagine an administrator mounts another filesystem at:
/data


Before mounting, /data contained some files.

After mounting, those files appear to disappear.

What happened?

The new filesystem is now visible through the /data mount point.

The original directory contents are hidden underneath the mounted filesystem.

They are not necessarily deleted.

Unmounting the filesystem can reveal the underlying directory contents again.

This is a classic Linux operational behavior and is one reason mount operations must be planned carefully.

Part 10 — Advanced engineering concepts
10.1 Static versus variable data
This is an important design principle behind the filesystem hierarchy.

Static data does not change frequently as the system operates.

Variable data changes during normal operation.

Examples:
Static or relatively static	Variable
Installed software	Application logs
Shared libraries	Cache entries
Documentation	Runtime state
System programs	Database state
Configuration	Queue contents

Historically, Unix-like systems separated static and variable data partly to support mounting some filesystems read-only and applying different backup and maintenance policies.

The FHS discusses this design rationale, particularly the separation between /usr, /etc and /var. 

Debian+1

Modern deployments do not necessarily mount /usr read-only, but the organizational principles remain useful.
10.2 Shareable versus unshareable data
The FHS also distinguishes data that can conceptually be shared between systems from data that is specific to one machine.

For example:
- Shared software resources may be suitable for sharing between compatible systems.
- Host-specific configuration belongs to the individual system.
- Runtime process information is specific to the currently running machine.
- Application logs usually belong to the machine producing them.
This is part of the reasoning behind the established filesystem hierarchy.
10.3 Filesystem hierarchy versus mount namespace
This is an advanced concept.

Linux processes do not always see exactly the same mounted filesystem tree.

Linux supports mount namespaces, which provide different mount views to different processes.

For example:
Host system mount view
        |
        +-- /data
        |
        +-- /home
        |
        +-- /var


A container could receive a restricted mount view:
Container mount view
        |
        +-- /
        |
        +-- /app
        |
        +-- /tmp


A container process might not see the host's entire filesystem.

This is one of the foundations behind container filesystem isolation.

We will study mount namespaces in Stage 03, Module 08.
10.4 Why /proc and /sys are important to observability
Observability means collecting information that helps us understand what a system is doing.

Consider a monitoring program.

It may need to inspect:
- Process IDs.
- CPU information.
- Memory information.
- Network interfaces.
- Block devices.
- Kernel counters.
Some of this information is exposed through /proc and /sys.

A monitoring agent can collect it and send it to an observability platform.

A simplified workflow:
Linux kernel
     |
     +---- /proc
     |
     +---- /sys
              |
              v
       Monitoring agent
              |
              v
       Metrics collection
              |
              v
       Monitoring platform
              |
              v
       Dashboards and alerts


These interfaces are therefore essential to Linux infrastructure monitoring.
10.5 Why directory permissions matter
The filesystem hierarchy defines where files live, but permissions determine who can access them.

For example:
/etc/myapp/config.yaml


The location may be correct, but the application might still be unable to read the configuration.

Likewise:
/var/lib/myapp/


may be the correct location, but an application may fail if its service account does not have write permission.

This shows that three separate concerns work together:
1. Hierarchy determines where information belongs.
2. Ownership and permissions determine who can access it.
3. Filesystem and mount behavior determine how that information is stored and exposed.
We will study the second concept deeply in Module 02 and the third in Stage 02, Module 05.

Part 12 — Common mistakes and misconceptions
These should be emphasized when teaching because they are common sources of Linux administration failures.
Mistake	Correct understanding
Treating /root as the root filesystem	/ is filesystem root; /root is the root user's home
Storing application logs in /etc	Logs ordinarily belong under /var/log
Treating /tmp as permanent storage	Temporary files may be cleaned automatically
Treating /proc like an ordinary disk directory	It is a virtual kernel interface
Treating /sys as a normal data directory	It exposes device and kernel subsystem interfaces
Assuming /bin is always a physical directory	It can be a symbolic link to /usr/bin
Assuming /usr contains personal documents	It primarily contains installed software and shared resources
Deleting large files under /var without investigation	First identify the application and purpose of the data
Assuming /mnt/c is the native Linux filesystem	It represents Windows storage mounted into Linux
Assuming every application puts data in /var/lib	Application storage locations depend on implementation and configuration
Assuming all Linux machines have identical directory layouts	The filesystem hierarchy allows distribution and system-specific differences
