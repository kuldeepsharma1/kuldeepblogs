# **Part 1 — Orientation: Understanding Linux**

Before teaching someone Linux commands, establish one important idea:

**Linux is not just a command-line interface. It is an operating system ecosystem that powers servers, cloud infrastructure, containers, supercomputers, embedded devices and much of the technology behind the internet.**

A terminal is simply one way to interact with it.

## **1.1 What is an operating system?**

An operating system (OS) is the software layer that manages a computer's resources and provides services to applications.

Imagine a computer has:

- A processor (CPU) that executes instructions.
- RAM that holds data currently being used.
- Storage that keeps data when the machine is turned off.
- Network interfaces that communicate with other machines.
- Applications that need access to all these resources.

Without an operating system, every application would need to manage hardware and resources independently. That would be extremely complicated.

An operating system provides a common management layer.

**Simplified operating system architecture**

**Applications**

Web server · Database · Browser · Developer tools

**Operating system services**

Processes · Files · Users · Networking · Services

**Kernel**

CPU scheduling · Memory · Devices · Filesystems · System calls

**Hardware**

CPU · RAM · Disk · Network · Devices

For example, suppose a web server wants to save an uploaded file.

The web server does not directly control the physical storage hardware. It requests a file operation through the operating system. The kernel and filesystem implementation handle the necessary work.

This separation makes it possible for many applications to share hardware safely and efficiently.

## **1.2 What is Linux?**

Technically, **Linux is the kernel**.

The kernel is the central component of an operating system. It manages the computer's hardware and provides controlled access to system resources.

The Linux kernel is responsible for areas such as:

| Responsibility     | What it means                                                       |
| ------------------ | ------------------------------------------------------------------- |
| Process management | Creating, scheduling and terminating processes                      |
| Memory management  | Allocating RAM and managing virtual memory                          |
| Filesystem support | Providing filesystem operations                                     |
| Device management  | Interacting with hardware through drivers                           |
| Networking         | Implementing network protocols and interfaces                       |
| Security           | Enforcing permissions and other access controls                     |
| System calls       | Providing the interface applications use to request kernel services |

A kernel is not the entire user experience.

A Linux kernel alone does not automatically give you a convenient terminal, shell, package manager, standard utilities or administration tools.

You need additional software.

## **1.3 What is a Linux distribution?**

A Linux distribution, commonly called a *distro*, combines the Linux kernel with a collection of other software to create a usable operating system.

A distribution typically provides:

- Linux kernel and kernel-related tools.
- A shell such as Bash.
- Standard utilities such as `ls`, `cp`, `grep` and `find`.
- A package management system.
- System libraries.
- Service management tools.
- Default security policies and configurations.
- Software repositories.
- Release and security maintenance policies.

Think of the kernel as the engine and the distribution as the complete vehicle assembled around that engine.

This analogy is useful, but remember that distributions can use different kernels, configurations, libraries, tools and release policies.

For example:

- Ubuntu uses the Debian packaging ecosystem.
- Debian is an independent distribution and the upstream base for Ubuntu.
- Red Hat Enterprise Linux (RHEL) uses the RPM packaging ecosystem.
- Amazon Linux is designed for AWS environments and uses the RPM/DNF ecosystem in Amazon Linux 2023.

These are not merely different visual themes. Their administration practices and software lifecycles can differ significantly.

## **1.4 Linux versus distribution versus shell versus terminal**

These four terms are frequently confused.

| Term         | Meaning                                               | Example          |
| ------------ | ----------------------------------------------------- | ---------------- |
| Linux        | The operating system kernel                           | Linux kernel 6.x |
| Distribution | A complete operating system assembled around a kernel | Ubuntu 26.04     |
| Shell        | A program that interprets commands                    | Bash             |
| Terminal     | An interface through which you interact with a shell  | Windows Terminal |

The relationship looks like this:

```
You
 │
 ▼
Terminal application
 │
 ▼
Shell (Bash)
 │
 ▼
Linux programs and utilities
 │
 ▼
System calls
 │

 │

```

A terminal does not execute Linux instructions by itself. It provides an interface to a shell. The shell interprets your commands, starts programs and coordinates their input and output.

Later in this module, we will study precisely how this command-execution process works.

## **1.5 Where does WSL fit into this architecture?**

The learner uses Windows, so it is important to understand what is happening when they open Ubuntu from Windows Terminal.

**Windows Subsystem for Linux (WSL)** allows Linux distributions and Linux tools to run alongside Windows.

There are two architectures:

- **WSL 1:** Uses a compatibility layer that translates Linux system calls into operations supported by the Windows kernel. It does not run a real Linux kernel.
- **WSL 2:** Uses a real Linux kernel inside a lightweight, Microsoft-managed virtual machine.

Microsoft documents WSL 2 as the default architecture for new installations. It provides much broader Linux system-call compatibility than WSL 1.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://learn.microsoft.com\&sz=32)

Microsoft Learn+1



**What happens when Ubuntu runs in WSL 2?**

**Windows 11 / Windows 10**

Your primary operating system

**Windows applications**

Browser · VS Code · Windows Terminal

**WSL 2 managed virtual machine**

A lightweight virtualized Linux environment

**Microsoft-provided Linux kernel**

**Ubuntu distribution**

Bash · apt · Linux utilities · libraries · applications

The key distinction:

- Windows remains the main operating system.
- WSL 2 provides a Linux kernel environment.
- Ubuntu provides the distribution and its user-space software.
- Bash provides the interactive command interpreter.

The Linux environment is real enough to teach most Linux administration fundamentals, including processes, permissions, package management, networking and many system services.

However, WSL is not identical to a standalone production Linux server. Its kernel, hardware access, networking, device integration, lifecycle and virtualized environment introduce differences.&#x20;

# **Part 2 — Topic 01: Ubuntu, Debian, RHEL and Amazon Linux**

## **2.1 Introduction: Why do multiple Linux distributions exist?**

Imagine a company wants to operate 500 servers.

Another company wants to run a cloud application on AWS.

A third company operates banking infrastructure and requires long-term vendor support.

All three need Linux, but their requirements are different.

| Requirement                | What the organization values                              |
| -------------------------- | --------------------------------------------------------- |
| Software development       | Convenient tools, broad package availability              |
| Enterprise infrastructure  | Predictable changes, support contracts, compatibility     |
| Cloud infrastructure       | Cloud integration, optimized images, managed lifecycle    |
| Databases                  | Reliability, supported dependencies, predictable upgrades |
| Security-sensitive systems | Controlled updates, certifications, security policies     |

One Linux distribution cannot necessarily optimize for every organization's needs.

This is why different distributions exist.

They share many fundamental Linux principles, but differ in:

1. Who develops and maintains them.
2. How software is packaged.
3. How packages are installed and updated.
4. How releases are tested.
5. How long releases receive security updates.
6. What configuration and security defaults they provide.
7. What type of environments they target.

**Important engineering principle:** Linux knowledge is transferable, but distribution-specific administration knowledge is also necessary.

An experienced administrator understands both.

### **What does LTS actually mean?**

LTS does not mean the operating system will never change.

It means the release receives a longer maintenance commitment.

Suppose an organization deploys an application on Ubuntu 24.04 LTS.

It wants to avoid changing the underlying OS every few months because changes may affect:

- Application dependencies.
- Database compatibility.
- System libraries.
- Drivers.
- Runtime behavior.
- Operational procedures.

An LTS release gives the organization a longer period in which to maintain the same major release while receiving supported security and bug fixes.

An important technical detail: Ubuntu often backports security fixes instead of moving every package to its newest upstream feature version. This is intended to preserve compatibility while correcting vulnerabilities.&#x20;

**Debian**

Community-developed · DEB/APT ecosystem · Stability-oriented releases

### **What is Debian?**

Debian is an independent, community-driven Linux distribution.

It is one of the important foundations of the Linux distribution ecosystem.

Ubuntu is built using Debian as its foundation, but Debian itself is a separate operating system with its own governance, maintainers, repositories and release process.

### **Why does Debian exist?**

Debian places substantial emphasis on:

- Software integration.
- Stability.
- Predictable releases.
- Free and open-source software.
- Careful testing.
- Broad hardware and architecture support.

A critical concept here is that stability and newness are not the same thing.

A package that has been thoroughly tested and remains compatible over a long period may be preferable to a package that is newer but has not yet undergone equivalent integration testing.

This is especially important for servers.

### **Debian release branches**

Debian maintains three important development states.

**Stable**

Production-oriented

Software selected and tested for the official stable release. This is the normal choice for production deployments.

**Testing**

Integration testing

Packages being evaluated for a future stable release. It generally offers newer software but may experience changes and regressions.

**Unstable (Sid)**

Development

The continuously changing development distribution where new packages and changes are integrated.

Debian officially recommends Stable as its primary production release. Testing and Unstable have different purposes and should not be treated as interchangeable production environments.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://www.debian.org\&sz=32)

Debian+1



### **What does stable mean?**

Let's use a practical example.

Assume an application depends on:

```
Python
OpenSSL
glibc
PostgreSQL libraries
System utilities
```

A constantly changing operating system might introduce newer versions of some dependencies.

That may introduce:

- API changes.
- Behavior changes.
- Compatibility problems.
- Regressions.
- Unexpected application failures.

Debian Stable aims to keep the package set relatively consistent throughout a release's life.

This does not mean vulnerabilities are ignored.

Security fixes and selected bug fixes are applied while preserving the release's overall compatibility goals.

**Stable means controlled and predictable software changes, not that bugs are impossible.**

### **Debian package management**

Debian uses the DEB packaging system and APT.

The fundamental tools are:

| Tool        | Responsibility                                           |
| ----------- | -------------------------------------------------------- |
| `apt`       | High-level package and dependency management             |
| `apt-get`   | Script-oriented APT interface                            |
| `dpkg`      | Lower-level package installation and database management |
| `apt-cache` | Queries package metadata                                 |

Example:

```
sudo apt update
sudo apt install nginx
```

The package management principles are similar to Ubuntu because both distributions use the same underlying packaging ecosystem.

However, their repositories, versions, package builds and release policies are not identical.

### **Debian lifecycle**

Debian's Stable lifecycle is approximately five years: the Debian Security Team provides the initial security maintenance, followed by the Debian LTS team for the remaining period.

Debian 13, code-named Trixie, is the current Stable release as of November 2026. Its published lifecycle includes regular support followed by LTS through June 2030.&#x20;

## **3.3 Red Hat Enterprise Linux (RHEL)**

**Red Hat Enterprise Linux**

Published by Red Hat · RPM/DNF ecosystem · Enterprise-oriented

### **What is RHEL?**

Red Hat Enterprise Linux, commonly called RHEL, is an enterprise-focused Linux distribution published by Red Hat.

It is designed for organizations that need a professionally supported operating system with controlled release management, documented lifecycle policies and enterprise infrastructure integration.

RHEL is commonly encountered in enterprise data centers, application platforms, databases and large-scale business infrastructure.

### **Why does RHEL exist?**

Consider a large organization operating:

- 200 database servers.
- 100 application servers.
- 50 internal infrastructure servers.
- Several hundred virtual machines.

A major operating system change could affect thousands of business operations.

The organization therefore needs:

1. Predictable software maintenance.
2. Documented compatibility expectations.
3. Vendor support.
4. Security advisories.
5. Controlled minor releases.
6. Long support timelines.
7. Enterprise administration features.

RHEL addresses these requirements through its enterprise release and support model.

### **The RPM ecosystem**

Unlike Ubuntu and Debian, RHEL belongs to the RPM packaging ecosystem.

The RPM format means *RPM Package Manager*.

An RPM package commonly has a filename such as:

```
nginx-1.26.0-1.el10.x86_64.rpm
```

This is an illustrative filename.

RHEL uses two important software management layers:

| Technology | Responsibility                                             |
| ---------- | ---------------------------------------------------------- |
| RPM        | Low-level package installation and package database        |
| DNF        | Higher-level software management and dependency resolution |

In practice:

```
sudo dnf install nginx
```

DNF checks configured repositories, evaluates dependencies, downloads the required packages and coordinates their installation.

Red Hat documents DNF as the standard package-management approach in current RHEL releases.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://docs.redhat.com\&sz=32)

Red Hat Documentation



### **RHEL repositories**

RHEL software is distributed through repositories.

Repositories are structured collections of software packages and their metadata.

The package manager uses repository metadata to determine:

- What packages are available.
- What version each repository offers.
- Which dependencies are needed.
- Which package sources are trusted.
- What updates can be applied.

Repositories can be vendor-managed or configured by an organization.

For supported RHEL environments, access to Red Hat repositories and support services is tied to the applicable subscription and registration model.

This is different from a typical Ubuntu installation, where the standard Ubuntu archives are generally accessible without a commercial subscription.

### **RHEL release and lifecycle strategy**

RHEL uses a lifecycle with major releases, minor releases and individual maintenance updates.

Example:

```
RHEL 10
   |
   +-- RHEL 10.0
   |
   +-- RHEL 10.1
   |
   +-- RHEL 10.2
   |
   +-- Later minor updates
```

This is a conceptual illustration.

The purpose is to provide a stable major-version platform while delivering updates within that release.

Red Hat's documented lifecycle for RHEL 8, 9 and 10 provides ten years across the Full Support and Maintenance Support production phases, followed by an Extended Life Phase. Additional coverage can be available under optional offerings.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://access.redhat.com\&sz=32)

Red Hat Customer Portal



### **Why does this matter?**

Imagine an organization runs an application on RHEL 9.

It may need to keep the same major release because:

- The application vendor certifies only particular OS versions.
- Database drivers depend on specific system libraries.
- The business has validated a certain runtime.
- Compliance requires controlled infrastructure changes.

The organization can maintain that environment while applying supported updates.

This is an important part of enterprise Linux administration.

### **RHEL and security**

RHEL has a strong enterprise security ecosystem.

A particularly important technology is SELinux.

SELinux (Security-Enhanced Linux) provides mandatory access control.

It can restrict what processes may access, even when ordinary Unix permissions would otherwise permit an operation.

For example, a web server process might have permission to read a file under traditional Unix permissions but still be denied by SELinux because its security policy does not permit access.

We will study SELinux and AppArmor in Stage 02, Module 06.

Other enterprise-related concepts include:

- Security advisories.
- System auditing.
- Cryptographic policies.
- Vendor support.
- Configuration compliance.
- Controlled software updates.

## **4.1 What is a package?**

A package is a structured collection of software files and installation metadata.

Imagine installing Nginx manually.

You might need:

- The Nginx executable.
- Configuration files.
- Startup service definitions.
- Required libraries.
- Documentation.
- File ownership and permissions.
- Installation and removal metadata.

A package groups the software and describes how it should be installed and managed.

## **4.2 What is a package manager?**

A package manager is software responsible for installing, upgrading, querying and removing packages.

Without one, administrators would need to manually:

1. Find the correct application binary.
2. Download its dependencies.
3. Verify the files.
4. Copy them into appropriate locations.
5. Configure them.
6. Update their ownership and permissions.
7. Track installed versions.
8. Remove everything correctly later.

A package manager automates much of this process.

## **4.3 APT versus DNF versus dpkg versus RPM**

This is one of the most important concepts in this lesson.

Do not confuse package formats with package managers.

| Layer                           | Debian / Ubuntu | RHEL / Amazon Linux |
| ------------------------------- | --------------- | ------------------- |
| Package format                  | DEB             | RPM                 |
| High-level manager              | APT             | DNF                 |
| Low-level package utility       | dpkg            | rpm                 |
| Common repository configuration | `/etc/apt/`     | `/etc/yum.repos.d/` |

Think of it as two layers.

```
DEBIAN / UBUNTU

        apt
         |
         | Resolves dependencies,
         | retrieves repository metadata,
         | manages packages
         |
        dpkg
         |
         | Installs package files,
         | records package state
         |
      .deb files
```

```
RHEL / AMAZON LINUX

        dnf
         |
         | Resolves dependencies,
         | retrieves repository metadata,
         | manages packages
         |
         rpm
         |
         | Installs package files,
         | records package state
         |
      .rpm files
```

The high-level manager is generally what administrators should use for normal software installation because it manages dependencies.

The lower-level utilities are useful for inspecting or operating on individual packages.

Ubuntu's official documentation describes APT as the recommended approach for DEB package management, with dpkg serving as the lower-level tool. Red Hat documents the equivalent DNF/RPM relationship.&#x20;

## **4.4 Why can you not normally install a DEB package on RHEL?**

A DEB package and an RPM package use different packaging formats and metadata conventions.

For example:

```
nginx.deb
nginx.rpm
```

Both might provide the Nginx application, but their installation metadata, dependency declarations and package management systems differ.

The package manager cannot normally treat one format as the other.

There are conversion utilities, but conversion does not guarantee that the resulting software is compatible.

Even if you convert an RPM to a DEB format, it does not automatically resolve:

- Missing libraries.
- Distribution-specific configuration.
- Different service definitions.
- Package dependency incompatibilities.
- Different installation paths.
- Distribution-specific security policies.

**Professional rule:** Install software using packages designed for your actual distribution whenever possible.

## **4.5 Why are commands sometimes different?**

Consider installing Nginx.

Ubuntu:

```
sudo apt install nginx
```

Debian:

```
sudo apt install nginx
```

RHEL:

```
sudo dnf install nginx
```

Amazon Linux 2023:

```
sudo dnf install nginx
```

The package manager differs between the two ecosystems.

Another example is Apache HTTP Server.

Ubuntu/Debian generally use the package name:

```
sudo apt install apache2
```

RHEL and Amazon Linux commonly use:

```
sudo dnf install httpd
```

Notice something important:

The application is conceptually the same, but package names and service names can differ.

This is why copying deployment instructions between distributions without checking them can cause operational failures.

## **6.1 Windows architecture versus Linux architecture**

Windows and Linux have different operating system architectures, but both provide the fundamental capabilities applications require.

| Concept                           | Windows                             | Linux                                             |
| --------------------------------- | ----------------------------------- | ------------------------------------------------- |
| Kernel                            | Windows NT kernel                   | Linux kernel                                      |
| Main command interpreter examples | PowerShell, CMD                     | Bash, Zsh                                         |
| Common native filesystem          | NTFS                                | ext4, XFS, Btrfs                                  |
| Software distribution             | EXE, MSI, MSIX, package managers    | DEB, RPM, other formats                           |

## **6.2 WSL 1 versus WSL 2**

**WSL 1**

**Linux applications**

**WSL compatibility layer**

**Windows NT kernel**

Linux system calls are translated into operations supported by Windows. There is no Linux kernel running inside WSL 1.

**WSL 2**

**Linux applications**

**Linux userspace and system libraries**

**Real Linux kernel**

**Virtualized hardware**

Linux system calls are handled by a genuine Linux kernel inside the WSL-managed virtual machine.

Microsoft's comparison identifies full Linux kernel availability, much broader system-call compatibility and systemd support as important WSL 2 differences.&#x20;

## **8.1 Kernel and userspace are separate**

The environment in which ordinary applications and utilities execute.

It includes:

- Bash.
- `ls`.
- `cat`.
- Package managers.
- Web servers.
- Databases.
- Application runtimes.

```
| Process Management                             |
| Memory Management                              |
| Filesystem Layer                               |
| Networking                                     |
| Device Drivers                                 |
| Security Mechanisms                            |
|                                                |
+------------------------------------------------+
                       |
                       |
                 Virtual hardware
```

This boundary is fundamental to Linux.

An ordinary userspace program cannot directly perform arbitrary privileged hardware operations. It requests services through system calls and other supported interfaces.

## **8.2 What is a system call?**

A system call is a controlled interface through which an application requests functionality from the kernel.

For example:

A program wants to read a file.

Conceptual execution:

```
Application
    |
    |
    v
Request to open a file
    |
    v
openat() system call
    |
    v
Linux kernel
    |
    v
Permission checks
    |
    v
Filesystem operations
    |
    v
File descriptor returned
```

The exact internal execution involves several components, but the important point is that userspace requests kernel functionality through defined interfaces.

### **Example: Running&#x20;**`cat`

When the learner executes:

```
cat /etc/os-release
```

The sequence is conceptually:

1. Bash receives the command.
2. Bash resolves `cat` using its command lookup rules.
3. Bash starts the external executable, typically using an execution-related system call.
4. The `cat` program requests access to the file.
5. The kernel performs filesystem and permission operations.
6. File contents become available to the process.
7. `cat` writes those contents to standard output.
8. The terminal displays the output.

Later, we will investigate this process in considerably more depth when studying system calls and `strace`.

## **8.3 Why can distributions have the same kernel but different behavior?**

Because the kernel is only one component.

Imagine two systems:

```
System A:
Linux kernel
Ubuntu userspace
APT
Ubuntu system configuration

System B:
Linux kernel
RHEL userspace
DNF
RHEL system configuration
```

Even if both use closely related kernel versions, the systems can behave differently because their userspace components, libraries and policies differ.

For example:

- Different package managers.
- Different Nginx package versions.
- Different default security policies.
- Different service configurations.
- Different library versions.

### **Advanced concept: Kernel version versus kernel patches**

An administrator must not assume that a Linux kernel with a lower-looking version number is automatically insecure or outdated relative to another kernel.

Distributions often backport security and bug fixes into their maintained kernel versions.

That means a distribution might retain a kernel version while incorporating security patches from newer upstream development.

This distinction is particularly important in enterprise Linux troubleshooting.

**Version number alone is not sufficient security evidence.**

## **8.4 How does a package installation work internally?**

Consider:

```
sudo apt install nginx
```

Conceptually, the operation follows this sequence:

```
Administrator runs apt install nginx
              |
              v
APT reads configuration
              |
              v
APT examines available package metadata
              |
              v
Dependency resolution
              |
              v
Download selected packages
              |
              v
Package signature / integrity verification
              |
              v
Package installation by dpkg
              |
              v
Package database updated
              |
              v
Installation scripts may execute
              |
              v
Files and configurations installed
              |
              v
Installation completed
```

Some important details:

- APT is the high-level dependency manager.
- `dpkg` performs the lower-level package installation.
- The package database records installed package information.
- A package may contain maintainer scripts that perform setup tasks.
- Installation does not automatically mean a service is operational.

For example, installing Nginx and verifying that Nginx is running are two separate tasks.

This distinction will become important in our future services module.

## **8.5 What changes between distributions?**

Imagine installing the same Nginx software.

The application purpose is similar, but the system integration can differ.

| Component                   | Ubuntu                                | RHEL / Amazon Linux                |
| --------------------------- | ------------------------------------- | ---------------------------------- |
| Installation manager        | APT                                   | DNF                                |
| Package format              | DEB                                   | RPM                                |
| Package database            | dpkg database                         | RPM database                       |
| Repository configuration    | `/etc/apt/`                           | `/etc/yum.repos.d/`                |
| Typical Apache package name | apache2                               | httpd                              |
| Software repository policy  | Ubuntu archive and configured sources | Vendor and configured repositories |

It is possible that the same software uses different default configuration paths, system user accounts or systemd unit settings.

A Linux administrator must inspect the actual environment rather than assume every Linux distribution behaves identically.

# **Part 9 — Real-world production scenarios**

The objective is to teach the learner how distro knowledge is used in actual infrastructure work.

## **Scenario 1: Installation instructions are failing on a production server**

A developer receives these instructions:

```
sudo apt update
sudo apt install nginx
```

They connect to a production server and receive:

```
sudo: apt: command not found
```

### **What happened?**

The instructions assume a Debian-based distribution.

But the server might be running RHEL or Amazon Linux.

Those systems ordinarily use DNF rather than APT.

### **How would an experienced administrator investigate?**

First:

```
cat /etc/os-release
```

Then:

```
uname -a
```

Then:

```
command -v apt
command -v dnf
```

Suppose the machine identifies itself as Amazon Linux 2023.

The administrator understands that the software installation instructions are written for the wrong distribution.

The appropriate installation command is:

```
sudo dnf install nginx
```

### **Why not simply install APT on the server?**

Because installing another package-management executable does not transform the underlying distribution.

APT does not automatically give you Ubuntu repositories, Ubuntu dependency packages or Ubuntu-compatible configuration.

The correct approach is to use the native package ecosystem.

**Engineering lesson:** Always identify the operating system before applying deployment instructions.

## **Scenario 2: A developer installs a package, but the software does not start**

A developer reports:

> I installed Nginx successfully, but my application cannot connect to the web server.

They show:

```
sudo apt install nginx
```

The installation completed successfully.

A beginner may assume the software is now working.

An experienced administrator knows that installation and service availability are different states.

The next stage of investigation might involve:

```
command -v nginx
```

To determine where the executable is located.

```
nginx -v
```

To determine the installed Nginx version.

Then, on a conventional systemd-based host:

```
systemctl status nginx
```

To inspect service state.

The service may:

- Be stopped.
- Have failed during startup.
- Be listening on another port.
- Have an invalid configuration.
- Be restricted by security policy.

On WSL, `systemctl` availability depends on systemd configuration, so this final investigation must be adapted to that environment.

We will study actual service management in Module 03.

**Engineering lesson:** Package installation proves that installation succeeded. It does not prove that the application is operational.

## **Scenario 3: An application works on Ubuntu but fails on Amazon Linux**

A team develops an application on Ubuntu.

Their deployment script contains:

```
sudo apt install nginx
sudo apt install python3
```

They move the same script to an Amazon Linux 2023 server.

It fails.

The team notices that the distributions have different package managers.

They update the deployment process to detect the operating system.

Conceptually:

```
case "$ID" in
    ubuntu|debian)
        # Debian-family package installation
        ;;
    rhel|amzn)
        # RPM-family package installation
        ;;
    *)
        echo "Unsupported operating system" >&2
        exit 1
        ;;
esac
```

This is only the decision structure, not a complete production-safe installer.

The final implementation must also validate release versions, package availability, repository configuration and privileges.

**Engineering lesson:** Cross-distribution automation must account for distribution identity, package names, repositories and system configuration.

## **Scenario 4: A server is running an outdated operating system**

A company has been operating an old Linux server for years.

The application still works, but the operating system has reached the end of its security maintenance period.

The administrator needs to determine:

1. Which distribution is running?
2. Which release is installed?
3. Is the release still supported?
4. Which security updates are available?
5. Is an in-place upgrade supported?
6. Does the application support the newer release?

The investigation begins with:

```
cat /etc/os-release
```

Then the administrator checks the vendor's official release lifecycle documentation.

For example:

- Ubuntu: official Ubuntu release lifecycle.
- Debian: official Debian releases.
- RHEL: Red Hat Enterprise Linux lifecycle.
- Amazon Linux: Amazon Linux release cadence.

The administrator does not assume that every Linux distribution has the same five-year or ten-year support period.

**Engineering lesson:** An operating system's support lifecycle is part of production security, not merely a documentation detail.

# **Part 10 — Troubleshooting: Evidence before assumptions**

A professional Linux administrator should have a repeatable investigation process.

For distribution-related problems, use this sequence:

```
Problem reported
      |
      v
Identify the operating system
      |
      v
Identify the release version
      |
      v
Identify the running kernel
      |
      v
Identify the package ecosystem
      |
      v
Check repository configuration
      |
      v
Check package availability
      |
      v
Apply distribution-correct fix
      |
      v
Verify the result
```

## **10.1 Common problems and solutions**

| Symptom                                   | Possible cause                               | Investigation                            |
| ----------------------------------------- | -------------------------------------------- | ---------------------------------------- |
| `apt: command not found`                  | Not a Debian-based environment               | `cat /etc/os-release`                    |
| `dnf: command not found`                  | Not an RPM/DNF environment                   | `command -v dnf`                         |
| Package not found                         | Wrong name or unavailable repository         | `apt-cache search` or `dnf search`       |
| Package installation fails                | Repository or network problem                | Inspect package manager output           |
| Unsupported package architecture          | Wrong CPU architecture package               | `uname -m`                               |
| Application version differs from tutorial | Different distribution release or repository | Inspect package version                  |
| Service name differs                      | Distribution-specific package conventions    | Inspect installed package and unit files |
| WSL kernel does not match Ubuntu version  | WSL provides its own kernel                  | `uname -r` and `/etc/os-release`         |

## **10.2 Problem:&#x20;**`apt`**&#x20;command not found**

Investigate:

```
cat /etc/os-release
```

Then:

```
command -v apt
command -v dnf
command -v yum
```

Interpret the result.

If `ID=amzn`, an Amazon Linux system is likely using DNF in AL2023.

If `ID=rhel`, it is a Red Hat Enterprise Linux environment.

If `ID=ubuntu` or `ID=debian`, APT should normally be available in a standard installation.

Do not install a random package manager in an attempt to fix the problem.

## **10.3 Problem: A package is not found**

On Ubuntu:

```
apt-cache search nginx
```

This searches the package metadata available to APT.

To inspect a particular package:

```
apt-cache policy nginx
```

This displays available version and repository information.

On RHEL or Amazon Linux:

```
dnf search nginx
```

To inspect package information:

```
dnf info nginx
```

Interpretation:

- Is the package listed?
- Is a candidate version available?
- Which repository provides it?
- Is the required repository configured?
- Is the package name correct for this distribution?

An administrator should establish these facts before modifying repository configuration.

## **10.4 Problem: APT reports outdated package information**

APT maintains local metadata about package repositories.

When repository metadata changes, the local index may become outdated.

The correction is:

```
sudo apt update
```

What does this command do?

It downloads and updates local package index information from configured repositories.

It does not upgrade all installed software.

That is the responsibility of:

```
sudo apt upgrade
```

This distinction is important.

```
apt update
    |
    v
Refresh repository metadata
    |
    v
apt upgrade
    |
    v
Upgrade installed packages
```

## **10.5 Problem: WSL reports an unexpected Linux kernel**

Suppose the learner executes:

```
uname -r
```

And sees:

```
6.x.x-microsoft-standard-WSL2
```

They might assume Ubuntu installed the wrong kernel.

That conclusion is incorrect.

WSL 2 supplies a Microsoft-maintained Linux kernel for the managed WSL environment.

The Ubuntu distribution supplies userspace packages.

Check:

```
cat /etc/os-release
```

And:

```
uname -r
```

These outputs identify two different components.

Do not attempt to replace the WSL kernel with a conventional Ubuntu server kernel merely because the version string looks different.

# **Part 11 — Advanced engineering notes**

The following concepts help move the learner beyond basic Linux usage.

## **11.1 Upstream and downstream development**

These are common terms in open-source software development.

**Upstream** is the original project or source from which another project receives software or changes.

**Downstream** is a project or distribution that incorporates, modifies or packages upstream work.

Example:

```
Linux kernel project
        |
        v
Distribution kernel maintainers
        |
        v
Linux distribution package
        |
        v
Installed server
```

A similar relationship exists between Debian and Ubuntu.

Ubuntu incorporates large amounts of Debian work but also maintains its own changes and packages.

Why should an administrator care?

Because a software issue may originate in:

- The original upstream application.
- A distribution-specific patch.
- A package dependency.
- A repository release.
- Local system configuration.

Understanding the software's origin helps narrow down bugs.

## **11.2 Stable does not mean outdated**

Consider these imaginary versions:

```
Package upstream:
Version 5.0

Distribution release:
Version 4.7 + security patches
```

The distribution might maintain the earlier version while backporting security fixes.

A beginner sees `4.7` and assumes the software is vulnerable.

An experienced administrator checks:

- Distribution security advisories.
- Package release information.
- Backported patches.
- Installed package revision.
- Support status.

A version number alone is not proof that a vulnerability is present.

## **11.3 Why do package names differ?**

Linux packages are maintained by distribution-specific maintainers.

They can choose different names, split applications into different packages or organize dependencies differently.

For example:

```
Ubuntu:
apache2
```

```
RHEL:
httpd
```

These are different distribution packaging conventions for the Apache HTTP Server.

You should never assume that package names are universal.

## **11.4 Why are package repositories important?**

A package repository is a managed software source.

Think of it as a trusted catalogue of available software packages and metadata.

The package manager does not simply download random files from the internet.

It typically works with configured repositories and metadata, including integrity and authenticity mechanisms.

Administrators should be careful about adding third-party repositories.

An untrusted repository could introduce:

- Malicious packages.
- Vulnerable dependencies.
- Unexpected software replacements.
- Dependency conflicts.
- Packages with incompatible release assumptions.

### **Security principle**

Do not add an unknown package repository simply because an online tutorial tells you to.

Verify:

1. Who maintains it?
2. Whether it supports the actual distribution release.
3. Whether package signatures are verified.
4. Whether the repository is appropriate for production.
5. What packages it can replace or upgrade.

## **11.5 Distribution release versus kernel release**

A Linux server has multiple version numbers.

For example:

```
Distribution:
Ubuntu 24.04 LTS

Kernel:
Linux 6.x

Nginx:
1.x

OpenSSL:
3.x
```

These identify different software components.

Updating a package does not necessarily upgrade the whole distribution.

Similarly, upgrading the distribution does not necessarily mean every application immediately moves to the newest upstream version.

A good Linux engineer knows which component is being updated and what dependencies might be affected.

## **11.6 One WSL kernel, multiple Linux distributions**

This is a particularly interesting WSL 2 detail.

A WSL 2 environment can contain multiple installed Linux distributions.

For example:

```
Windows
  |
  +-- WSL 2 managed virtual machine
         |
         +-- Linux kernel
         |
         +-- Ubuntu distribution
         |     +-- Ubuntu root filesystem
         |     +-- Ubuntu packages
         |     +-- Ubuntu users
         |
         +-- Debian distribution
               +-- Debian root filesystem
               +-- Debian packages
               +-- Debian users
```

The distributions have separate Linux userspaces and filesystems, but share the WSL-managed kernel and certain resources.

Microsoft documents the namespace and resource-sharing behavior of WSL 2 distributions.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://learn.microsoft.com\&sz=32)

Microsoft Learn



This is similar to understanding the relationship between a shared kernel and isolated Linux environments.

We will revisit this idea in Stage 03 when studying containers and namespaces.

## **11.7 Why is WSL not a production server?**

WSL 2 is a highly useful Linux environment, but there are important differences.

| Area           | WSL 2                                        | Conventional Linux server                                        |
| -------------- | -------------------------------------------- | ---------------------------------------------------------------- |
| Kernel         | WSL-managed kernel                           | Installed and maintained in server OS                            |
| Boot lifecycle | Managed by WSL                               | Normal Linux boot process                                        |
| Hardware       | Virtualized and restricted                   | Hardware or hypervisor-controlled                                |
| Networking     | WSL virtual network integration              | Server network interfaces and routing                            |
| Storage        | Virtualized Linux storage and Windows mounts | Server block devices and filesystems                             |
| Kernel modules | Restricted by WSL kernel configuration       | Supported modules subject to kernel and hardware                 |
| Cloud metadata | Not inherently available                     | Available according to cloud provider and instance configuration |

This matters because some production tasks cannot be demonstrated accurately in WSL.

For this training path, use the following environment classification:

**WSL READY**

Normal practice

Shell commands, distribution identification, package management, permissions, many process operations, scripting and much of userspace administration.

**WSL LIMITED**

Special considerations

systemd behavior, system boot lifecycle, networking boundaries, some storage operations, resource management, device access and kernel investigation.

**VM REQUIRED**

Real Linux host

Realistic bootloader management, destructive partition exercises, unrestricted hardware experiments, custom kernel/module development and authentic RHEL or Amazon Linux host administration.

For this particular topic:

- Ubuntu identification and package management: WSL READY.
- Debian comparison: WSL READY if Debian is installed as a separate WSL distribution.
- Actual RHEL package management: VM REQUIRED for a faithful RHEL environment.
- Actual Amazon Linux administration: use a suitable Amazon Linux VM image where supported, or a disposable EC2 instance for AWS-specific validation.

There is no need to purchase cloud infrastructure to learn the current topic.

## **16.4 Important terminology**

| Term            | Meaning                                                              |
| --------------- | -------------------------------------------------------------------- |
| Kernel          | Core OS component managing hardware and resources                    |
| Distribution    | Complete operating system built around a kernel                      |
| Userspace       | Environment where ordinary programs execute                          |
| Shell           | Program that interprets commands                                     |
| Terminal        | Interface used to interact with a shell                              |
| Package         | Structured software installation unit                                |
| Package manager | Tool for installing and managing packages                            |
| Repository      | Managed collection of software packages and metadata                 |
| LTS             | Long-Term Support                                                    |
| Upstream        | Original software project or source                                  |
| Downstream      | Project that incorporates upstream software                          |
| Backport        | Applying a fix from newer development to an older maintained version |
| WSL             | Windows Subsystem for Linux                                          |
| VM              | Virtual machine                                                      |

## **16.5 Important misconceptions to eliminate**

**Linux is Ubuntu.**

Linux is a kernel. Ubuntu is one Linux distribution.

**All Linux distributions use APT.**

Ubuntu and Debian use APT. RHEL and Amazon Linux 2023 use DNF.

**WSL is just a terminal emulator.**

WSL 2 runs a real Linux kernel inside a lightweight virtual machine.

**The newest Linux package version is always the best choice.**

Production systems also require compatibility, security maintenance and predictable upgrades.

**All distributions with DNF are identical.**

Sharing a package-management tool does not make distributions or their repositories interchangeable.

**Installing a package means the application is running.**

Installation, configuration, service startup and application availability are separate operational states.

# **Final teaching takeaway**

The biggest conceptual achievement in this first topic is understanding that **Linux is an operating system foundation, while distributions provide different implementations and operational environments around that foundation.**

A Linux administrator should not simply know that Ubuntu uses APT or RHEL uses DNF.

They should understand why those tools exist, how distributions are maintained, how package repositories work, why release lifecycles matter, and how to identify an unfamiliar system before modifying it.

That is the difference between someone who can copy Linux commands and someone who can administer Linux infrastructure.
